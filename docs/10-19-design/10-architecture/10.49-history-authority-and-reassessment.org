* DESIGN WP08 objective and retained owners
:PROPERTIES:
:CUSTOM_ID: history-authority-and-reassessment
:STATUS: Target file/field/call/history design only; no implementation, authority act or review submission
:END:

WP08 takes the actual C/Q/R and current WP07 technical verification basis, discovers
the required authoritative history cut H, verifies actual roles/mandates, and
admits scoped decision records under the adopted policy. It preserves original
counter evidence and denials while supporting explicit repair, exception,
reconsideration, replacement and withdrawal. A decision can govern a declared
review purpose; it cannot change a false property into a true one.

Aitia's existing review/history/authority owners retain the domain meaning.
Core retains local receipt issuance/revocation, POO/Core owns Types and graph
algorithms, existing source/custody owners publish and recover accepted history,
and ASCENT projects accepted facts under WP06. There is no second ledger,
authorization engine, key directory, consensus service or generation registry.
WP09 owns recipient distribution/adoption/use; Runtime authorization and effects
remain separate even when a review is admitted.

The policy and permitted actions are published Library meaning, selected by
Profile and captured with project inputs in C. Actual project authority adopts
them and appoints people through real sources. This design does not appoint the
currently unassigned DE-CASE-01 roles or create their missing decisions.

* SPECIFIED Authoritative discovery and negative preservation
:PROPERTIES:
:CUSTOM_ID: authoritative-history-discovery
:END:

Required source demand comes from actual adopted project mandate/custody and
applicable policy: relevant technical/counter/failure sources, accepted decision/
denial/exception/withdrawal sources, role/grant/key-status sources and predecessor/
handover lineage. The submitter cannot choose only favorable intakes, directory,
root key or apparently empty record files. A genuine initial baseline needs an
authenticated no-predecessor/source mandate, not an absent directory interpreted
as a clean history.

Discovery performs these bounded operations at the existing owners:

1. Validate actual C/Q/R/technical use and trusted mandate/current directory/root
   selection. Determine the full required source inventory, project/family/scope
   relevance and status/continuity requirements independently of supplied records.
2. Obtain actual selected source heads/cuts, owned accepted record inventories,
   original origins/signatures/grants and predecessor closure. Resolve by actual
   source/custody context; no directory crawl, lexical latest-version selection
   or serialized reader capability substitutes for the selected source operation.
3. Check each required source's availability/currentness/accepted prefix and all
   relevant record/role/status references. Duplicate identities with incompatible
   content, forked heads, missing predecessor or an unavailable required source
   refuse complete discovery. Retain both offending candidates/known history.
4. Bind H to that exact source vector, required-versus-observed inventory, actual
   verifier/source/clock/limits and remaining findings. Recheck source selection
   and relevant status at receipt issuance and authority use; a reused query or
   cached signature still requires its actual full dependencies/currentness.

| Input state | Required interpretation |
|-------------+-------------------------|
| Authenticated accepted denial/counter in relevant history | Retain original scope/claim/policy/revision/origin, regardless of changed current policy or favorable new results |
| Accepted inventory names a negative record whose proof/artifact is unavailable | Discovery/authority remains incomplete or blocked; do not omit it or infer approval from failed verification |
| Arbitrary malformed/forged untrusted rejection submission | Retain rejection diagnostic at its actual intake; it is not an accepted authority denial merely because text says rejected |
| New policy or project revision excludes a formerly relevant scope | Require explicit authenticated lineage/impact/applicability reasoning under policy; preserve original decision/counter and exclusion rationale. New label alone does not clean history |
| Source disappears or returns an older/smaller accepted prefix | No silent shrink/reset. Verify genuine authorized continuity/retirement/replacement or block current use; prior negatives remain known |
| Sources expose incomparable concurrent heads | Retain conflict and refuse a unique current authority cut until actual authorized continuity resolves it; never choose the newest timestamp/hash |

Completeness is bounded to the independently mandated source universe, accepted
prefixes and declared freshness at H. It is not proof that no future or undiscovered
global event exists. A vector of observed remote/local cuts is not automatically
an atomic distributed instant. Unsupported freshness/consistency at the required
strength remains a gap; offline use needs actual explicitly adopted bounded
policy, not a guessed grace period.

:PROPERTIES:

:END:

| Operation / actual owner | Input -> output | Mandatory boundary |
|--------------------------+-----------------+--------------------|
| Discover / trusted project source adapter + Aitia | Actual C/Q/R/mandate and required source operations -> H and diagnostics | No raw directory/key/source list override; missing required source remains blocking |
| Verify discovery / Aitia through Core | Exact typed H request and actual current source/root/lineage checks -> real scoped receipt or diagnostic | Complete required coverage and actual current selection, not merely every supplied file passing a signature check |
| Prepare decision/reconsideration / actual project principal | Exact R/H/technical/findings and supported proposed action -> inert typed record/request | Proposal/Agent drafting is not a signed accepted decision, role appointment or authority receipt |
| Verify action / selected Aitia authority operation | Exact proposal/H/technical/grant/status/conditions and actual credential proof -> verified action finding/receipt or refusal | Check actual principal, scoped permission, policy authority, delegation, quorum and independence; no signature-only or public technical.admitted? acceptance |
| Accept record / existing authority/custody owner | Verified exact action and expected prior selection -> accepted immutable record/prefix or refused/unknown publication | Recheck actual source/grant/current technical basis and source head; serialize under genuine host custody; preserve all known accepted negatives on ambiguity |
| Evaluate current use / actual Aitia owner | R, current H, original accepted decisions and fresh technical/authority/status verification -> scoped admission assessment or blockers | Validate decision applicability and every relevant denial/conflict/condition; old frame/receipt cannot answer changed accepted inventory |
| Reassess / project adapter + existing method/content/Aitia owners | Retained old basis/failures/denials plus actual changed inputs/new evidence -> new scoped technical/review/authority associations | Repair verification and decision replacement are separate acts; no implicit deletion or reinterpretation of original evidence |
| Withdraw/revoke / target's actual owner | Authenticated targeted withdrawal or actual local revocation request -> retained status change and current-use effect | Root/grant/decision/Core-receipt/evidence-use/owner have distinct owners; do not mutate unrelated historical records |

Preconditions are action-specific. An authorized rejection or deferral of a
recognized truthful R with pending/counter/conflict, or a targeted withdrawal,
does not require the positive technical result that it denies or withdraws.
Otherwise the protocol could suppress precisely the negative records it must
preserve. Require valid target/provenance and actual authority for that action,
retain the incomplete technical basis, and grant no positive use permission.
Positive review admission separately needs the policy's actual technical/
context/content/role conditions and any genuinely permitted current exceptions.
Neither an arbitrary malformed intake nor an unauthorized rejection becomes an
accepted denial through this distinction.

For each action verify the principal and credential against trusted roots/current
status; authentic appointment and grant/delegation chain; project/family/R/purpose/
action/scope and conditions; actual validity and permitted delegation depth;
required risk/decision roles, distinct-principal quorum and independence. A child
grant cannot widen its parent or delegate an ungranted action. Delegation cycles,
ambiguous root rotation and contradictory grants block that action. Two keys or
signatures from one principal do not fill a two-principal requirement. C1's Agent
cannot appoint itself independent reviewer or decision authority.

The actual policy states whether prior valid decisions survive ordinary grant
expiry/role retirement and which later revocations affect current use. Preserve
historical validity at acceptance separately from current eligibility: expired
or rotated credentials do not erase an old denial. Conversely, a historical
signature cannot bypass an effective targeted withdrawal/compromise/use restriction.
No arbitrary caller may backdate a grant or turn its own key into a trust root.

The native gate must receive actual current WP07 technical assessment/use through
the trusted producer, with the matching R/C/Q/policy/project basis. For positive admission it additionally
requires the actual policy-defined context/content/semantic/role coverage and
conditions; negative/defer/withdraw actions use their own legitimate preconditions. A caller-created object with admitted?=#t
cannot replace it. Core receipts are checked through the actual selected adapter
and WP07 fresh-time/source rules. Reuse actual Assurance Decision preflight or
Cedar/Runtime handoff only where its real claim/action mapping is qualified;
preflight or a permit-shaped request is not review acceptance or an effect grant.

* SPECIFIED Repair, exception and authorized replacement
:PROPERTIES:
:CUSTOM_ID: repair-exception-decision-replacement
:END:

| Kind of change | Required evidence/authority | Retained fact and limit |
|----------------+-----------------------------+-------------------------|
| Property repair | Actual changed semantic inputs, new method/content A/E/W/U, old-to-new claim/domain/correspondence and independent repair interpretation under declared policy | Original counter/failed attempt stays historical. Same case/payload or changed source digest alone cannot prove repair |
| Missing evidence supplied | Actual new qualified method/content output/use and full required coverage, with new Q/R as needed | Old missing/timeout record remains history; a new observation is not a rewrite of its completion |
| Accepted bounded exception | Policy must permit that particular exception; authentic risk/decision authority, exact unmet duty/counter, use scope, rationale, mitigation, expiry and reopen trigger, plus actual required approvals | False remains false and the duty remains visibly excepted/unmet as defined. No waiver of truth, identity, real authority or mandatory non-exceptable conditions |
| Denial supersession | Exact original accepted denial IDs, genuine reconsideration/impact basis, actual authority for that denial/scope and current policy, correct lineage/conditions and explicit new record | Denial is retained, not deleted. A favorable technical finding, new policy string or an approval not naming it cannot supersede it |
| Decision replacement | Explicit predecessor records, scope/lineage/impact rationale, real replacement authority and complete coverage | New decision does not silently rewrite project revisions, product state, W or earlier record bytes |
| Withdrawal or loss of a resolution's current eligibility | Authenticated target/status or genuine local receipt revocation, current-policy/coverage reassessment and other live qualifying resolutions if any | Formerly covered denial/duty becomes blocking again unless another genuinely eligible scoped resolution covers it; no permanent erase bit |

A repair finding explains a technical claim, not permission to override a prior
rejection. An accepted exception can permit a specified risk-bearing review/use
only under the actual adopted policy; it is not support for the violated property
or permission to deploy. Exception requested, exception authorized and exception
currently usable remain distinct. Expired conditions/mitigations or an unsupported
risk authority prevent current use; no generic ignore-counter option is exposed.

Replacement/supersession edges must reference actual accepted records, be scope-
and action-correct, unambiguous and acyclic. Reuse Core graph/DAG analysis for the
declared relation; it does not itself authenticate the edges. A replacement can
cross policies/revisions only through explicit verified project lineage and actual
permission to address the old decision. No lexical revision/timestamp ordering,
last-file-wins, green majority or unsigned forward-reference closes a denial.
Concurrent independent rejection and approval stay retained; current denial blocks
until genuinely authorized resolution under the relevant policy. Repair/exception/
supersession coverage must include every affected required case/criterion; a fix
for M04 cannot silently dispose of M06 or an unrelated rationale requirement.

* SPECIFIED C/Q/R, history and acceptance ordering
:PROPERTIES:
:CUSTOM_ID: history-decision-acceptance-order
:END:

A decision refers to its finalized C/Q/R, technical basis and predecision history
H0. It is then appended to the actual accepted prefix, yielding H1. Do not require
its signature to hash the future H1 containing itself. Current-use discovery of
H1/H2 verifies the original H0 lineage, record inclusion and every subsequent
relevant decision/withdrawal; it does not rewrite the original signature to name
a newer cut. Fresh Core request receipts can bind that current frame with the
original record as an input, preserving both origins.

Before append, action verification establishes the exact proposed record's
authentication/permission at its predecision basis. It is not proof that the
record was accepted. After actual append/publication, a current authority frame
verifies accepted-record inclusion, original authorization and current policy/
status/denial coverage against H1/H2. Any Core request/receipt must distinguish
these assertions and include its exact action, stage and target. A proposal or
preflight receipt cannot be replayed as an accepted decision merely because
its record bytes match; the actual accepted source owner establishes inclusion.

A history-only authority update can create a new authority frame H/use for the
same technical R when its technical meaning remains unchanged. If new history
changes required technical evidence, comparison/coverage or Q facts, obtain the
appropriate new Q/R; changed captured products/adoption/grants/policy inputs need
new C. Do not rerun unrelated Rust/QNT/Lean/SysML just to rediscover an authority
record. Any later ASCENT history/status projection follows actual accepted native
records into a subsequent identified Q; it cannot create or certify the decision
that was its own input.

The existing authority owner/custody publisher serializes expected prior selection
-> verified action -> accepted record/prefix publication -> current selected head.
Qualify what that host actually guarantees about exclusivity, fencing, ordered
write/close/sign/head selection and durable observation. A before/after head hash
is not by itself cross-process compare-and-swap, and file rename is not universal
distributed durability. Missing stronger guarantees leave that route unsupported;
this design does not create a consensus service to paper over them.

| Boundary / failure | Required result |
|--------------------+-----------------|
| Proposed action malformed/unauthorized or unsupported | Reject diagnostic; not an accepted decision/denial and no durable authorization |
| Source head/grant/technical basis changed before acceptance | Refuse/reprepare current frame; no favorable stale commit |
| Accepted negative known but prefix publication fails/is ambiguous | Retain the accepted negative/actual attempt; make that owner unusable for positive admission until genuine current custody/recovery qualifies. Never rewind to an older favorable frame |
| Receipt or decision accepted but later export/acknowledgement fails | Preserve the real accepted/issued state and uncertainty of export; do not claim a rollback across owners or invent a successful publication |
| Process loss or incomplete writing state | Unknown/unusable current authority until actual selected-head/accepted-prefix and reader activation/repair qualify; files alone cannot reconstruct private Core receipts |
| Required source advances after a successful frame | Old frame stays historical; current operation must use a new current discovery/verification basis or block |

Signature/exchange/Session/file/publisher operations are distinct owners. Failure
in one does not erase a genuine earlier action in another. Preserve actual
attempts, partial outputs and accepted origins. All discovery, graph checks,
credential verification, publication and rechecks use declared finite budgets/
footprints and retain real timeout/unknown outcomes; no timeout widening or
synthetic heartbeat turns incomplete authority into an admission.

* SPECIFIED Revocation, current use and custody recovery
:PROPERTIES:
:CUSTOM_ID: authority-withdrawal-and-recovery
:END:

| Target/status change | Correct owner and exact consequence |
|----------------------+-------------------------------------|
| Core verification receipt | Actual issuer calls poo-flow-revoke-verification!; subsequent real admissions fail for it. This does not erase original evidence/decision records or automatically publish a project withdrawal |
| Evidence/qualified use | Actual method/content producer and WP06 source adapter withdraw current eligibility; W/E and counters remain. Affected Q/R/technical/decision use is reassessed |
| Role/grant/credential/root | Actual project trust/status authority authenticates the effective action/target/scope, rotation/delegation lineage and impact. Preserve prior records; derive current eligibility from actual policy/status, not deleted key files or labels |
| Accepted review decision/exception | Actual authorized decision/status owner records targeted withdrawal/expiry/conditions. Keep the original acceptance and reasons; re-evaluate dependent denial coverage and uses |
| Owner/reader retirement or head rollback/fork | Existing custody owner closes the live capability and checks actual selection/lineage/fencing; no old frame/reader resumes current authority by restoring a file |
| Required status source unavailable | Currentness/discovery is unestablished at the required strength; cached old positive state is not a fresh permission |

Revoking a decision-verification receipt, revoking a grant, withdrawing a decision,
repairing a property and replacing a denial are different operations. A revoked
resolution receipt or status can reopen the original denial for current use;
it cannot expunge that denial, authenticate a forged new rejection, or fabricate
a different principal's revocation authority.

Reuse WP07's actual trusted clock/lease/source-currentness mechanism and fresh
Core admission at each use. An old indexed admission does not track a moving
clock; a still-valid request seal does not discover current role/decision/status
changes. Observed invalidation remains recorded; old bytes returning cannot
resurrect revoked private receipts or retirements. Where policy permits restored
unchanged-basis verification, it is a genuine fresh operation with its actual
origin, not resurrection of the old authorization.

Recovery/handover uses actual closed source/predecessor identity, expected accepted
prefix/original origins and grants, selected signed current head, fresh actual
reader/activation and retirement of known old live owners. Archive integrity is
only a custody fact; successor verifies original decisions and role/status scope
again, including every retained denial. A storage-prefix repair only completes
the exact authorized interrupted byte prefix under its expected selection; it
cannot approve a project, drop a denial or rewrite an original signature. Later
activated/current heads reject replay of an old repair/activation/handover grant.
Fresh local reader bookkeeping is not a global single-reader proof across hosts;
the actual source/host selection guarantee must be qualified at its stated scope.

Local revocation and accepted withdrawal discovery are distinct from propagation
to recipients. WP09 needs actual recipient/use/status associations and fresh
verification. There is no instantaneous global revocation over disconnected
hosts, and this design neither sends notifications nor performs an external
revocation action. Any permitted offline window must be explicitly authorized
and bounded by the adopted policy; otherwise unavailable current status blocks.
