* DESIGN WP10 scope and acceptance meaning
:PROPERTIES:
:CUSTOM_ID: case-joint-acceptance-plan
:STATUS: Joint qualification design only; no implementation, acceptance execution, review submission or delivery
:END:

WP10 qualifies the complete DE-CASE-01 slice against the actual selected policy:
checked Library publication -> Profile selection -> unique Scenario C -> actual
method/content A/E/W and qualified use -> determinate Q -> exact R and independent
context/content verification -> authoritative history and scoped accepted actions
-> exact authorized delivery -> recipient-owned verification, capture, review,
adoption and current intended use. WP00's supported source/compiled/cold/recovery
lane is mandatory for the corresponding end-to-end claim.

This plan defines future executable controls, artifacts, owners and gates. It
does not declare the target refactoring implemented, populate missing reviewer
appointments, issue evidence, authorize any real operation or supply an acceptance
result. Role names below assign engineering responsibility, not actual people.
Org/D2 lint/render success is documentation validation only.

Acceptance is a conjunction over an independently declared finite requirement
inventory and required lanes. It is not a count of green assertions, majority
vote, report status, execution exit code or timestamp winner. Known negative
controls must succeed by producing the specified refusal/counter/pending result
and preserving the required history. A rejected use can be correct behavior;
that test pass is not permission for the rejected operation.

The final policy/scope/roles/source/trust inputs and concrete expected control
matrix must be bound before execution. Today's design does not pretend that a
runnable, adopted plan or current C already exists. Missing preconditions leave
the affected gate blocked and the full slice unqualified.

** SPECIFIED Source, compiled and cold distinctions

Source lane means actual source-mode selection/loading of the relevant project
units in a fresh process, with explicitly identified precompiled dependency
closure where required. It does not mean every dependency was interpreted.
Compiled lane means actual qualified compilation and inspection of loaded output
for every unit covered by the claim, including tests/adapters where required.
Do not infer either lane merely from a launcher named gxi or a .ss/.ssi argument.
An earlier compiled test path check covers its named units only; WP10 extends
actual provenance to the selected required closure.

Cold here means a new process/VM, no inherited live C/W/receipt/admission/Session
or trusted reader cache, an explicit loadpath and fresh attempt outputs. It is
not a claim that OS page caches are empty, and does not require deleting global
package caches or historical data. Archived evidence may be supplied explicitly
as data; each new process re-establishes real current local verification/custody.
Separate fresh-rebuild qualification from fresh-process use of retained compiled
artifacts. Both must name actual inputs; neither proves the other's behavior.

Ordinary cold/recovery runs must finish all planned cases, harness/oracle checks
and natural exit zero under the fixed limit, including shutdown. A last passing
assertion followed by timeout/kill, a stale source cut, zero discovered cases or
an incomplete phase sequence cannot pass. Resource admission and semantic
correctness remain separate reported dimensions.

** SPECIFIED Recovery and receiver scope

Ordinary recovery requires every producer/restart-one/restart-two/restart-three
phase and complete DR01-DR21 expectations at the new target semantics. Handover
requires both current groups, exact predecessors/accepted negatives and retired
writer refusal. Durable intake and prefix repair retain every declared killed
boundary, actual partial bytes and later fresh-process refusals/authorized repair.
A signature-cache hit still checks complete current byte/status closure; a batch
must preserve the prior accepted cut on precommit failure and distinguish actual
postcommit export failure.

Process interruption qualification does not establish power-loss/fsync or general
distributed crash atomicity. Any stronger required deployment boundary must have
its real storage/fencing/transport owner qualified separately. No before/after
hash or local reader map is promoted to distributed serialization.

Receiver qualification needs a distinct actual project root and custody/process,
with its own project assumptions, roles/policy/trust adoption and C/Q/R, not only
a copied producer report or renamed Profile. Test a permitted declared operation
through its real use owner. General cross-host/offline claims require that actual
route's independent trust/current-status and effect-boundary controls; a same-host
isolated receiver establishes only that narrower scope. Runtime deployment is
outside this slice unless separately and explicitly selected/authorized; no
review/adoption result grants deployment implicitly.

history state. Reject module/check/case/harness errors, heap/stack overflow,
truncation, stale inputs, skipped mandatory cases and missing artifacts even if
some marker or public passed field exists.

actual process/boundary marker, exact interrupt record and byte closure, matching
runner status and later independent recovery checks must all agree. Exit 137
alone can mean watchdog/OOM/unrelated termination and never passes. An ordinary
phase requires natural zero exit; timeout 124 or termination after watchdog fails
that phase even if partial gold appears. Preserve the cause and observed grace.

The unchanged failed ordinary-recovery route must not be rerun to seek a lucky
pass or closed by widening limits. First qualify a concrete source/runtime/build
repair at its real owner, retain old failures, then run the affected exact new
basis within the declared limits. An independently adopted new support envelope,
if ever needed, is a separately identified scope and cannot rewrite old failure.
No such repair, scope change or execution occurs in this task.
