refactoring, not an implemented pipeline. No implementation, dependency, generated

is run. Org and D2 are updated explicitly. Existing model/receipt bytes retain
10.80's meaning and limits. Earlier plans remain target requirements; they do not
become available APIs merely by appearing in a design table.

* What is a declaration, and what is accidental hardcoding?
:PROPERTIES:
:CUSTOM_ID: chain-audit-classification
:END:

| Keep as authored declarations or framework reuse | Required distinction |
|------------------------------------------------+----------------------|
| Project source paths, explicit Module IDs and example runner's chosen Profile | Concrete composition is legitimate. A reusable entry must expose its supported selections; fixed example imports do not demonstrate dynamic Library selection |
| LIB-C01--C03, D01--D10, role/owner names and project model names | These describe this case. Publish domain policy in Library, select applicable policy in Profile, bind project occurrences in Scenario |
| Independent Library demand and candidate offers | Preserve both sides. Deriving all offers automatically from required items would hide missing coverage; common identity references may be shared without sharing the truth of satisfaction |
| ASCENT relation declarations, finite result states and fixed resource limits | These are executable semantics and execution policy. They need ownership and validation, not arbitrary user-editable strings or unbounded execution |
| Native define-program, open-session and replace-sources! | Retain upstream evaluation, incomplete-result handling and transactional semantics. A domain-to-relation adapter is necessary and is not a second inference framework |
| SysML keywords, sorting and serialization helpers | Language syntax belongs in the projection adapter. Project identity, catalog resolution and authority to choose a candidate do not belong there |

Declarative does not mean that an LLM can rewrite protected rules or choose a
provider by an unchecked string. The LLM proposes intent/candidate/model edits;
confirmed intent and selected policy constrain them. ASCENT computes consequences
from the admitted inputs. Core binds actual providers. Explicit selection and
validation determine which consequence can become a model candidate.

not equivalent to DE-PROJECT in the renderer. The former are semantic vocabulary

* Target organization and call boundaries
:PROPERTIES:
:CUSTOM_ID: chain-audit-target
:END:

The following are responsibility boundaries for the existing owners, not a new
directory scheme, universal pipeline object or public tuple-based configuration
language. Public extensible values remain ordinary POO objects with inherited
Types/Contracts. Pure projection/serialization algorithms remain named functions.

| Owner | Publishes / selects / captures | Consumes and returns |
|-------+--------------------------------+----------------------|
| Project | Explicit source root, supported Modules and their dependency bindings; declared Profile/Scenario entry selections | Core selection/linking returns admitted Scopes. Unsupported providers refuse before reasoning. Root model describes the project; it is not an executable loader |
| Library | Reusable organization/model vocabulary, obligations and applicability, two policy definitions where required, LR method definition and SysML projection method/catalog; sole contract generation source | Publishes through Config/interface and Core Scope Contracts. Identity, contract generation and semantic revision remain separate. No version in Namespace or Org-owned registry |
| Profile | Select Library/model/policy/method identities from published capabilities, candidate allocations, proposed refinements, explicit materialization policy | Consumes admitted Scopes; does not reconstruct Library Config behind Scope checks. Project goal and selection are references, not claims that runtime evidence already exists |
| Scenario | Bind confirmed intent occurrence, actual repo/input acquisition, selected parent/policy/method closure and candidate-specific plan to one C | Retain admitted normalized subjects and origin associations under the supported Core/producer protocols. Project associations are checked here; fresh verification/current use is separate from immutable C |
| Application reasoning Module | LR01--LR08 domain program, fact projection and bounded query interpretation | Consume the same C through the checked adapter; call upstream ASCENT; retain all conflicts/gaps/invalidated alternatives, declared source coverage, method/program identity and result association. This slice's result is not yet the complete determinate Q of 10.70 |
| SysML projection method | Supported language/model mapping and deterministic rendering/validation | Consume the selected candidate/plan and C-bound consequences; resolve actual catalog elements, validate candidate bytes and closure, return candidate artifacts/status. No provider selection, capture issuance or review authority |
| Org/D2 and content observation | Explain goal, selected architecture, decisions, obligations, source references and current/historical status | Display the same declared identities and recorded associations. Future content observers check actual bytes/references. Existence of a generated file cannot discharge a content or verification duty |
| Aitia / downstream assurance | Independently review applicable policy, content and evidence when that later boundary is implemented | Receives its required C/Q/evidence association, never a ready string as authority. Remains outside this refactoring slice's execution |

The selected Core's module-system/selection/init-syntax.ss already exposes the
literal poo-flow! entry, profile/extends forms and init.build-spec/init.build-run
projections, with profile composition delegated to its existing user-profile owner.
Use those supported mechanisms where the selected cohort qualifies them; do not
introduce a parallel Project registry or another provider-resolution loop. Core
user-profile settings and the domain LibraryFormationProfile have different
responsibilities; reuse supported composition without treating them as one schema.
At the Contract boundary, selected Core types.ss already normalizes through value-contract,
classifies, collects responsibilities/obligations, and returns evidence.candidate;
poo-flow-contract-validate returns that accepted value. Reuse this algebra rather
than duplicating field Types in a Scenario-specific validator. This source inspection
does not establish that every downstream Context/Scope caller preserves the return.

Library owns an application rule definition; the executable Module exposes it using
ASCENT. This is compatible with preserving the existing engine owner. It does not
require moving LR code into upstream ASCENT or adding an application evaluator.
Similarly, publishing a SysML model Library is distinct from an adapter writing
SysML text: both must be selected and their associations checked.

The intended manual call sequence is:

1. Project declares providers; Core admits Context, dependency Scopes and final
   Scope. Preserve each normalized return; the known handoff repair requirements
   in 10.76 must be qualified rather than assumed fixed in this cohort.
2. Profile selects published organization/model/policy/method definitions. Record
   the user-confirmed intent and candidate provenance separately from observations.
3. Scenario acquires actual inputs and prepares one admitted C. The report and
   execution consume that same C; no second invocation manufactures its substitute.
4. Application projection produces a complete declared batch and calls the existing
   ASCENT Session. Record coverage and result-to-C/program association. A partial
   caller batch must not be promoted to a complete project interpretation.
5. Explicit selected policy permits a candidate to be materialized. The SysML method
   consumes its bound plan, resolves the catalog and validates generated bytes.
6. An explicit publication operation may promote a validated candidate, retaining
   the previous root and failed alternatives. Org and D2 record the corresponding
   selection, obligations and evidence status; automatic synchronization is not added.

No step here authorizes an LLM to manufacture observations, authorize its own
candidate, silently weaken demand, treat absent facts as global absence, or mutate
Core's provider set at runtime. Adding supported declarations can extend a model;
new semantics or new executable providers require their own reviewed declarations
and qualified implementation.

implementation is authorized.

* Open items and bounded completion
:PROPERTIES:
:CUSTOM_ID: chain-audit-open
:END:

The current slice has no published general SysML catalog selection, full effective
Contracts, authenticated C/result binding, trusted capability admission, complete
build/load/recovery qualification or model publication protocol. The exact supported
Core origin/currentness API and any upstream gap must be established against the
chosen cohort before implementation; 10.77's design is not proof of that facility.
These are explicit refactoring prerequisites, not reasons to build parallel issuers.

Still to decide in declarations: reusable versus case-specific policy inheritance;
which materialization policy each Profile selects; candidate-specific versus shared
layout applicability; supported SysML element kinds/qualified-name behavior; and
which previously authored root changes must be preserved or reconciled on promotion.
Keep unresolved choices visible. No automatic LLM loop, repository scanner, arbitrary
provider discovery, model merge engine, review submission or delivery is added here.

Correctness requires identity/closure, declared semantics, preserved negative
outcomes and honest current-use boundaries. Whether an LLM assisted by ASCENT improves
architecture quality, review cost or decision robustness remains a research question
requiring separate comparisons. Baseline gap counts, route parity and static SysML
validation do not establish that research result.
