* DESIGN WP02 objective and boundary
:PROPERTIES:
:CUSTOM_ID: library-objects-and-publication
:STATUS: Object/configuration/link/publication design only; no implementation or execution
:END:

WP02 turns the Types/Contracts in 10.42 into coherently constructed and published
Library values. It fixes where each object obtains its parent, policy, mapping,
delta, configuration and expected Contract, and what actually crosses a Scope
boundary after validation. Public objects remain POO values/prototypes and
specializations; algorithms remain named functions. Existing Core Module linking
is the publication mechanism. No additional Library registry, factory manager,
configuration language, version service or fact store is introduced.

The shared BackpressureDeclarationContract in abstract/types.ss remains the sole
V1 generation owner. Definitions reference their own expected role Contract;
role descriptors reference that shared owner. Objects, Config, interface,
mapping generators, Profiles, Org and D2 author no replacement version value.

This is a complete target design for WP02. WP01 expected Contracts and the Core
checked-value handoff correction below are prerequisites. Actual capture,
execution, evidence/query interpretation, review and delivery still belong to
WP03-WP09, with WP00/WP10 qualification. Publication describes capabilities and
binds actual deferred operations; it does not execute or approve them.

Source imports form an acyclic graph: POO/Core -> abstract Types -> Generic
objects -> Generic Config/interface; abstract Types -> Rust Types -> Rust objects;
implementation bindings consume Types/definitions; interface joins these owners
with the actual dependency binding. Core role discovery imports present roles;
it is not permission to depend on their textual discovery order. Any needed
Types/object reference has its explicit import/binding. Types never import objects
back; objects never retrieve their parent from init or their assembled interface.

A pure specialization helper may remain implementation-local if it helps express
POO composition. Public extensibility is the POO definition/prototype and checked
Scope value, not a new builder protocol. The current specialize-backpressure and
resource-slice-entry APIs are migrated directly with active callers. Neither a
public factory beside a published slice nor a generic-entry/parent pair remains
as a second live source of meaning.

The [[file:10.55-library-construction-and-scope-handoff.org::#s2-core-candidate-handoff][S2 handoff design]] fixes the required-edge record meaning: retain the
original provider Scope/evidence/source record, keep consumer-specific accepted
requirement-evidence, and bind the alias from that evidence's candidate. Do not
patch provider.scope with an edge-normalized view while leaving its original
Scope evidence attached. Final linked scope instead uses scope-evidence.candidate;
the existing publication candidate path already does the correct handoff. These
are target migrations at Core, not changes made by this documentation task.

* SPECIFIED Construction and normalization order
:PROPERTIES:
:CUSTOM_ID: library-object-construction-order
:END:

| Stage | Binding / output used by the next stage | Required checks and limits |
|-------+----------------------------------------+----------------------------|
| 1. Admit Generic configuration and definition | Checked Config.entry under the expected Generic role; complete Generic Scope under BackpressureScopeContract | Real root identity/revision/contract/parent=false; complete duties/assets/premises; one family owner; publish checked functions/values |
| 2. Resolve Rust's required Parent | Actual Generic Scope returned from that required-edge admission, with provider/source/evidence association | No direct import of abstract/objects to bypass selection; no same-label reconstructed parent or process-global lookup |
| 3. Construct/check Rust specialization | POO extension of that admitted Generic entry; returned checked Rust value | Own identity/revision/contract; parent=that actual Generic entry; preserve inherited duties/dependencies/assumptions; complete child->parent state map |
| 4. Construct/check integration | POO extension of that returned checked Rust value; returned checked integration value | Own identity/revision/contract; parent=the exported Rust value; inherited meanings plus mapping/deltas and complete M01-M06 RL/SI/TM association |
| 5. Construct/check policy | Separate policy POO value referencing the applicable admitted role/family associations | parent=false; actual reusable criteria/product/responsibility/history rules; no model inheritance, actual project adoption or decision |
| 6. Assemble produced Scope and bind deferred operations | One Scope relating the checked definitions, expected role/family/parameter/Context descriptors and actual typed callables | Cross-export relationship checks operate on effective checked values; advertised callables must have real qualified implementations at their claimed strength |
| 7. Core admits/stores/returns Scope | Candidate returned in Scope admission evidence, with retained source/dependency/currentness association | Correct Core handoff from the audit; failed admission publishes no usable partial Scope/cache entry. Consumers read through existing currentness guards |
| 8. Scenario later selects | One published leaf/parent/policy association and supported requests | WP03 captures actual occurrence C. Selecting base Rust does not execute SI/TM or silently select integration |

Bind each dependency/checked definition once within this construction. References
in descendants must point to the checked predecessor, not a captured raw candidate.
All later Scope/required-edge normalizations must preserve coherent relationships
and use their returned receivers. Do not assume every validator preserves eq?
identity or that revalidating functions cannot add wrappers. POO receiver-aware
rebinding and the actual value normalization behavior must be exercised by tests.
If normalization changes a referenced predecessor, the effective descendant must
follow that checked binding before it can pass contextual association; do not
accept a stale lexical parent merely because fields compare equal.

Declaration references are opaque association fields, not invitations to recursively
execute each other's Contract methods. Common role metadata/field checks and
actual contextual parent checks remain separate, as in 10.42. Acyclic engineering
parent chains and a policy referencing role descriptors do not create a recursive
objects -> Types -> objects import or an eager descriptor self-validation loop.

Construction is once per actual successful linked Scope under Core ownership,
not a new global singleton guarantee. A failed attempt, new source context or
another link can yield another construction. Different admitted provider graphs
must not share accidentally cached parents/definitions. Declaration publication
performs ordinary validation and in-memory composition; it does not read project
workspaces, hash tool installations, run external methods or issue authority.

| Rust specialization / rust.resources.backpressure-memory / backpressure/v3 | contract=RustResourceModelContract; parent=actual admitted Generic; Rust lifecycle and explicit six-row child->parent map from 10.42; preserve generic duties/dependencies/premises and add existing BP/TR/CA/RL responsibilities, runtime-premises/design/trajectories and supported capabilities |
| Integration / rust.resources.backpressure-memory.integration / backpressure-integration/v1 | contract=BackpressureIntegrationContract; parent=the checked exported Rust; preserve its effective model and duties; add exact case-links, SI/TM dependencies/capabilities, mapping and deltas. | Backpressure review policy / rust.resources.backpressure-memory.review-policy / bounded-coding-method-review | contract=BackpressureReviewPolicyContract; parent=false; applies-to the actual supported Rust/integration role associations; own criteria/products/responsibilities/reconsideration. Definition remains proposed until implemented/admitted; it grants nobody authority |
| Design-review policy / rust.resources.backpressure-memory.design-review-policy / actual source-authored semantic revision required | contract=BackpressureDesignReviewPolicyContract; parent=false; distinct applicable design/content/history/authority/delivery criteria and requirements. Same declaration family, separate policy identity and expected descriptor; no project adoption or grant |

Rules and dependency extensions retain the meaning of inherited rows. A duplicated
obligation ID with another meaning is rejected; an identical repeated row is a
construction error to remove at its owner, not an excuse to merge contradictory
lists at use time. Changed meaning/assumptions/deltas need their actual semantic
revision decision and source binding. There is no automatic revision increment
or attempt to preserve current applicability merely by retaining a label.

The Rust state projection is waiting->waiting, queued->queued,
cpu-running->active, result-pending->returned, cleanup->cleanup and
released->released. Current active->cpu-running notation is deliberately migrated
to the convention selected in 10.42. Event/QNT states running/done remain a
separate mapped vocabulary; do not treat their labels as the engineering model's
parent-state relation.

Policy composition means an explicit applicability/required-obligation association,
not inheritance or copying project choices into reusable objects. The bounded
coding-method policy can distinguish the worker-owned M01-M05 review purpose from
M06 investigation while retaining all selected duties and negative history. It
cannot turn M06 into a safe result, remove a mandatory inherited obligation, select
a project's revision or sign a disposition. A Profile requests a published policy;
Scenario/project authority verifies its applicability/adoption under WP03/WP07.

This bounded policy does not cover every DE-CASE-01 architecture/Org/decision duty.
An actually published applicable design-review policy and real project mandate
must cover those duties before that broader review can be admitted. Adding this
backpressure policy export does not close GA09/GA18/GA24. A genuine standard
mapping is separately declared/adopted; the current SWE-061/class-a fixture is
not made the default or universal policy by moving it into objects.ss.

* SPECIFIED One mapping/delta owner and representation consumers
:PROPERTIES:
:CUSTOM_ID: library-mapping-delta-ownership
:END:

The selected integration definition's mapping and deltas are the sole authored
semantic values in rust/objects.ss. Types own their expected field/relationship
Contracts. Generator/observer code owns implementations of those declarations;
source/asset identity and correspondence duties connect implementation to meaning.
A reference or digest establishes identity, not semantic fidelity by itself.
No independent top-level Scope.mapping/Scope.delta copies are needed: consumers
read integration-entry.mapping and integration-entry.deltas from the selected value.

| Owned part | Concrete target meaning / consumer boundary |
|------------+---------------------------------------------|
| Mapping identity and revision | One authored association for current single-job observed cuts, linked to the integration semantic baseline and source assets. Generators/report serializers read it; remove independently maintained mapping literals |
| Input domain | The declared six-case workload with unique owned payload/permit premises, one admitted job and the qualified parameter domain; required event inventories, ordering/cut premises and actual result origin are explicit |
| Engineering/event/QNT correspondence | Explicit mapping of event-state transitions and observed synchronized cuts to the bounded abstraction; do not conflate lifecycle projection with event ordering or erase unobserved intervals |
| Case associations | Exactly (RL-M01,SI-M01,TM-M01) through (RL-M06,SI-M06,TM-M06), with corresponding six factors and declared evidence strengths; no generator invents another case list/duty catalog |
| Projection losses | Synthesized abstract states and bounded cut/path coverage are declared; no universal scheduling, memory-allocation, liveness or Rust-refinement claim follows |
| Queued-cancellation delta | A typed domain record identifies the affected parent model/premise and M02 duties. Guard: job is queued. Effect: remove it from queued and add it to cleanup; preserve admitted ownership and all other state fields. Cleanup draining remains a separate transition |
| Delta frame/obligations | Preserve limit, queueLimit, admitted, running, returned and done at that transition; account for parameter/job domain and links to original/extended-model checks. Keep base-model evidence distinct from delta/correspondence evidence |
| QNT generator | Consume the selected delta/mapping, render the supported transition and expected ordered path; unsupported/unrenderable declarations refuse that method. The hardcoded cancelQueued string cannot remain an independent authority for semantics |
| SysML generator | Consume the same mapping/case/cut contract and render actual supported assertions; missing domain/mapping support is a gap rather than a different implicit model |
| Method/observer | Bind actual declared source/semantic assets, generator/checker/tool closure and upstream Rust result; independently check generated content/result at the declared strength under WP04 |

These are typed POO domain values and bounded transformation responsibilities,
not a new general-purpose transition DSL or prose-to-proof engine. The renderer
must be qualified against the declared guard/effect/frame and supported model
schema using independent semantic controls. Moving a transition's label/rationale
into an object while leaving unchecked behavior hidden in a renderer would not
satisfy WP02/WP04. Changes to generators or relevant semantic assets affect method
footprints even if the declaration's revision label is unchanged.

* SPECIFIED Config choices and full Scope exports
:PROPERTIES:
:CUSTOM_ID: library-config-and-scope-publication
:END:

Generic Config keeps one entry selection under a closed Config value Contract
named BackpressureConfigContract (identity backpressure-memory/config) in
abstract/types.ss: its entry is an authored Generic value admitted under
the expected role/source association. The default reference is BackpressureModel,
not a copy of its fields. It does not accept arbitrary candidate-supplied Contracts,
providers, versions or project parameters as configuration. Any future supported
authored variant would need an explicit declaration and capability design first.

Rust Config has no behavioral options in this target. Its closed no-options
Contract is RustResourcesConfigContract (identity rust-resources/config) in
rust/types.ss; Config supplies that explicit no-options value.
The present unused purpose marker is removed in the coordinated implementation.
This is the existing Config role with an explicit meaning, not a wrapper Module.
The interface obtains the parent through requires and definitions through objects;
there is no Config.parent, Config.integration-entry factory, policy copy, hidden
latest lookup or project root. Scenario/Profile choose actual use later.

| integration-entry / integration-contract | Not advertised by Generic | Checked integration whose parent is Scope.entry / BackpressureIntegrationContract |

| methods / method-contracts | Actual supported generic callables and corresponding expected Function Types | Actual supported specialization/integration callables and corresponding expected Function Types; semantic definitions remain separate from implementation availability |

The Scope identity/export names remain those in 10.42; no generation suffix is
added to Module identities, semantic namespaces or filenames. No flat version field,
parent alias, global catalog bundle or second constructor is added to the public
Scope. Rust's required Generic Scope is retained by Core dependency records; a
second exported generic-entry is unnecessary because entry.parent is authoritative.

Every advertised callable has its actual expected input/output Contract and source
association. Publishing an integration value advertises its declared meaning;
method availability still requires a real supported implementation. Missing tools
at a project use do not delete integration duties or force tools to execute during
linking. An unimplemented method/capture route must remain explicitly unavailable;
WP02 cannot claim complete executable publication with procedure-shaped stubs or
always-true Types while waiting for WP03/WP04.

The complete WP02 publication includes the WP05 design-policy sibling. Construct
and check it at the same rust/objects.ss owner against its own expected descriptor;
Scope admission checks both fixed export associations. Supported content callables
use the existing methods/method-contracts field pair and real deferred operations.
Neither declaration nor Scope construction executes them. Their real bodies
must exist before public Scope exposure even though same-C runtime qualification
occurs later in WP04/WP05. Coordinated caller/producer migration may keep a draft
interface unpublished; a real checked Scope must never expose placeholder bodies. PB policy/export/callable
controls cover the added role occurrence without adding a model parent or another
version field. Generic Config still selects its authored entry; Rust Config stays
the closed no-options value. Profile chooses between published policies later.

A guarded previous Scope may remain historical/otherwise valid for its exact
basis, but must not be relabeled as a successful new publication after failure.
In-place source mutation and attempted restoration retain their actual object/read
revision behavior. All references in future evidence/capture include the selected
provider/descriptor/definition closure; filename/namespace changes are not version
management. Source and compatible compiled-loading paths require separate actual
qualification, including exact loaded-object association.
