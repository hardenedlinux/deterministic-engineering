* DESIGN Objective, research object and evidence boundary
:PROPERTIES:
:CUSTOM_ID: s6-aitia-review-adaptation
:STATUS: File/field/call/causal-claim/receipt design only; no implementation, verification or review submission
:END:

S6 consumes actual recognized C and its complete policy-required determinate Q,
prepares inert owned R, independently verifies context, inventory and criterion
assertions, and retains a scoped technical assessment/current-use association.
Policy adoption, project/source revision, actual roles, products and evidence remain
explicit. Receipt validity, semantic adequacy and decision authority are separate.
No appointment, submission, exception, release or delivery authority is created.

The user-designated research object is Pietrantuono et al.,
[[https://arxiv.org/abs/2605.02454v1][Causal Software Engineering: A Vision and Roadmap]], arXiv:2605.02454,
4 May 2026; [[https://arxiv.org/html/2605.02454v1][full text]], especially Sections 2-4. The paper proposes causal
assumptions, intervention records and evolving models, with an evaluation agenda.
We study its claims, limits and alternatives rather than treating its roadmap as
a requirement or its terminology as our architecture. It is a vision paper, not
an implemented protocol or evidence of this project's causal capability.

The mappings below are this repository's design proposals, not mechanisms claimed
by the paper. Treat causal justification as a substantive content-review concern
when the selected claim requires it. Do not classify every formal proof, dependency
edge or normative authorization as empirical causality. A valid seal can bind an
unsupported claim faithfully; it cannot supply missing identification or evidence.

* SPECIFIED Research the proposal through existing ownership
:PROPERTIES:
:CUSTOM_ID: s6-paper-to-framework
:END:

| Proposed project responsibility | Existing target owner / required boundary |
|----------------------------------+------------------------------------------|
| Decision question and claim kind | Library criterion declares expected claim/strength; Profile selects applicable review, Scenario binds project question. Distinguish observed fact, formal conditional/model result, empirical effect, model counterfactual and empirical incident counterfactual; normative approval remains authority work |
| Explicit causal basis where demanded | Content criterion refinement references exact hypothesis/model, intervention/comparator, outcome/unit/population/window, measurement, assumptions and identification argument. A SysML requires/read/call edge is not automatically a causal edge |
| Planned versus observed intervention | Project products distinguish proposed experiment from actual executed change. S3 captures prior spec/data/log inputs; S4 operations create new observations, never retroactively insert future experiment outputs into C |
| Supported analysis and uncertainty | Actual source-qualified method supplies estimate/domain/uncertainty/diagnostics and execution/input origin, or explicit not-supported. Deterministic Q checks accepted justification facts; it is not itself an effect estimator or causal discovery engine |
| Challenge and review | S4b binds attributed findings to precise assumptions/data/claim; S6 independently checks content assertion and reviewer role. Qualified sensitivity/refutation results remain distinct from software timeout or missing data |
| Change and use | Changed environment/data/assumptions/measurement/target population triggers actual applicability and transport checks, new C/Q/R as affected. Technical review cannot infer safe production action; S7 owns grants and decisions |

Use existing EngineeringProductContract, ContentCriterionContract and
ContentReviewFindingContract refinements plus actual A/Observation/use fields.
Causal evidence roles are selected by an explicitly supported criterion, not
mandatory statistical fields for unrelated locator or arithmetic claims. No new
verification purpose, Library generation, schema registry, causal fact service,
automatic CRL certification or universal causal-score gate is introduced.
Paper citation/version is an external reference identity, not a Library version.

| Selected causal criterion input role | Concrete required content / limit |
|---------------------------------------+-----------------------------------|
| question / target | Exact intervention X, alternative/comparator, outcome Y, units/population/service boundary/time window and estimand or exact model-counterfactual proposition |
| model / assumptions | Variable/measurement definitions, proposed causal graph/equations where applicable, hypothesized confounders/concurrent changes, selection/missingness/interference/stability assumptions and provenance; a drawn DAG alone proves no identification |
| design / identification | Actual experimental or observational identification route, assignment/comparison/adjustment assumptions and why relevant; unsupported or unmeasured requirements stay undetermined, not assumed away |
| observations / operation | Actual data/intervention/context/measurement lineage and aligned execution window, tools/recipe/estimator/source/configuration and complete footprint; planned log is not an observed intervention |
| finding / uncertainty | Actual estimate or bounded model conclusion, uncertainty interpretation and its assumptions, diagnostics/refutation/sensitivity findings, contrary results, scope/transport limits and attributable review |

These describe expected captured or actual derived input associations, not numerical
claims produced here. If no qualified estimator/data/identification route exists,
only hypothesis/specification/unsupported status can be reviewed honestly. No
QNT/Lean theorem or ASCENT support row silently becomes an empirical effect estimate.
Counterfactual claims require the supported model and assumptions for that precise
claim; a model alternative trace is not an observed alternate history of an incident.

Network-service illustration: changing retry/backoff while downstream capacity,
traffic composition and cache state also change cannot by itself establish that
the retry policy caused an observed latency change. Our proposed R must bind the
actual question, comparison, workload/measurement/assignment basis and unclosed
assumptions; without those, retain a candidate explanation and a missing causal
justification unit. This example is a design exercise, not a new experiment or
an estimate. DE-D04's capture architecture can be reviewed structurally without
pretending it has demonstrated performance benefits or incident prevention.

role/mandate/independence at its declared cut; it does not establish semantic content.

not establish adequacy. Review-content-criterion checks its exact assertion at

packages alone are no independent review. Shared qualified infrastructure may be
allowed without claiming independent authorship or methodology.

what the real operation established. A valid context seal cannot replace missing

operation/finding has its own origin, not fabricated shell execution or re-executed
human thought. Inaccessible inputs and unsupported causal identification remain
undetermined; a successful parser or complete Q cannot repair them.

* SPECIFIED Assessment, partial operations and retained negatives
:PROPERTIES:
:CUSTOM_ID: s6-assessment-and-negatives
:END:

Maintain separate axes for binding conformance, context, inventory accounting,
per-criterion finding, independence coverage, current evidence/receipt/source use
and remaining authority. Technical eligibility is exact policy-scoped interpretation,
not release permission. Required all/alternative/correlated/control/semantic coverage
is independent of whichever receipts happen to exist.

Missing source/product/role/data/identification or incomplete check remains explicit
pending/unsupported/unknown, not false architecture or favorable pass. A qualified
refutation remains counter; opposed comparable conclusions remain both with exact
claim/basis/scope. Distinct actual/target, run-local, formal/empirical or inventory/
adequacy claims are not blindly contradictory. Neither majority green, latest-looking
revision nor an authenticated assertion resolves semantic disagreement.

M06 harness success, Lean proved negation and QNT path reachability retain their
S4a polarity/limits. For causal claims, a failed identification prerequisite blocks
support without proving zero effect; a robustness check or absence of found
confounders cannot alone establish universal identification. A policy may require
recording unsafe alternatives/uncertainty without declaring the positive property
true. Exceptions and denial resolution require actual S7 authority and retain the
original finding. The paper supplies motivation, not a waiver or trust root.

If context issues but criterion times out, keep actual receipt and failed attempt;
if export fails after issuance, do not claim Core rollback. Recheck before any
current aggregate use. Known observed invalidation cannot be erased by restored
bytes. Process loss without terminal association stays unknown; files alone cannot
reconstruct private issuance. Full negative history discovery remains S7 work.

* SPECIFIED Receipt lifetime, invalidation and replay
:PROPERTIES:
:CUSTOM_ID: s6-receipt-use-and-replay
:END:

Core seals only after actual operation returns exact #t and copied request snapshot
is stable before/after. Receipt/admission/adapter identity and revocation stay private
to its real owner. Validity is [issued-at, expires-at), not a live dependency check.
Core validates caller-supplied exact instant/interval, not clock trust. Aitia's actual
configured common Host supplies bounded lease/trusted instant, rollback/source-cut
observations and fresh checks; caller now/until or fixture time cannot authorize use.
Keep clock units/domain/restart limitations explicit, without claiming portable time.

| Event | Required current-use response |
|-------+-------------------------------|
| Same permitted R/purpose/assertion/basis within lease | Reuse original receipt only after fresh actual role/source/evidence/status checks and Core admission at current trusted instant; technical assertion may be reusable |
| Changed C/Q/project/dirty source/policy/product/role/criterion/assertion | Different actual request basis; reprepare/reverify affected C/Q/R as appropriate, never generation-label/equal-hash shortcut |
| Expired, future, revoked, edited/copied receipt or foreign/modified adapter | Refuse current use through actual expected owner/private identity/snapshot/interval; retain historical diagnostics |
| Dependency/issuer/checker/grant/status drift inside valid seal interval | Fresh Aitia use refuses; actual owner invalidates/revokes affected local receipts where observed. Frozen snapshot validity alone cannot keep live use current |
| Known stale source returns to old bytes | Old invalidated association remains blocked; genuine fresh verification/status basis may issue new receipt, never resurrect old seal or erase transition |
| Later counter/history/withdrawal or environment/data assumption change | Refresh actual applicability/transport/history and affected use/Q/R/C. Unchanged technical Q/R may remain historical while later authority use is blocked |
| Cross-process/host/restored artifacts | Genuine compatible source/custody/current verification or unsupported-use gap; JSON/signature/private IDs cannot deserialize another process's receipt authority |

A Core admission indexes the supplied instant; retained admits? does not become a
moving clock. Build/check fresh admission on each use and after long operations;
expiry or role drift between independent checks blocks the aggregate. Two receipts
and source/status guards are not an atomic global authority/filesystem transaction.
Unsupported stronger race guarantees remain explicit.

Do not reject all equivalent request values blindly: Core seals value meaning,
while trusted adapter resolves exact expected purpose/assertion/R and selected
operation. Reusing original receipt for the same permitted technical assertion is
not cloning a receipt or replaying it for a different criterion/action. One-use
submission/disposition/effect semantics belong to S7/Runtime owner, not a new S6
nonce database. No cached admission verdict, copied key or receipt count grants action.
