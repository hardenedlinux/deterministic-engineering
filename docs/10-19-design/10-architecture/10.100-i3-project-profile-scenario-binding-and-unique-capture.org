* Scope and the single-capture invariant
:PROPERTIES:
:CUSTOM_ID: i3-binding-scope
:END:

This unifies 10.92 with 10.97--10.99 for the current Library Project. It specifies
changes to existing declaration, selection and acquisition seams; no implementation,
acceptance run, tool execution, actual capture, review, publication or orchestration
extension is performed here. The following names describe target roles/fields and
call boundaries, not APIs already implemented by Core.

#+begin_example
Project declared providers -> I0 compatible source/load cut
 -> Core K1 / actual provider S1 / consumer SD
 -> I2 admitted Library and Module offerings + checked Scenario Config
 -> normalized ProfileRequest + ProjectRequest -> BoundSelection
 -> actual expected bounded acquisition -> normalized owned basis
 -> expected origin verification -> final checked C
 -> inputs(C), methods(C), reason(C) -> later accepted inference view
 -> candidate selection/plan/materialization/validation -> separate explicit effect
#+end_example

One C means one original acquisition occurrence and its immutable semantic basis
shared by this slice's consumers. It does not mean one global C for a repo, one C
for all Profiles, or equal digests identifying the same issuance. Later A/E/W/use,
currentness findings, inference views, model candidates and review outcomes refer
to C; they are not appended to or substituted into its original basis. Reacquisition
creates a new C even when bytes are equal. A cold process cannot regain issuer
recognition by deserializing a capture record.

* Project graph, Scope handoff and consumer isolation
:PROPERTIES:
:CUSTOM_ID: i3-binding-project
:END:

Project owns the finite supported provider graph and the requested activity. Existing
Project init keeps Organization Library, formation Module and formation Scenario as
declarations. A resource/integration activity additionally declares the required
Generic/Rust domain and evidence providers at the actual owning interfaces. A
formation-only activity does not force unrelated Rust/tool providers. Once a route
requires a provider, Profile selection cannot erase a failed mandatory edge; a
narrower activity needs its own declared dependency route, sharing pure algorithms.

| Boundary | Producer obligation | Consumer obligation |
|----------+---------------------+---------------------|
| Core Context admission | Keep K1 = EK.candidate; actual current guards and paired provenance | Consumers use K1; no K0 fallback or invented authorization from copied fields |
| Provider final Scope | Record/facade preserve S1 = ES.candidate after actual final normalization | Select declared provider/alias and export; no raw object/import side door |
| Consumer dependency admission | Preserve SD = ED.candidate under that consumer's K1 | Factory reads its own actual SD, not provider S1 or the ED envelope |
| Scenario Config and exports | Retain checked Config; bind operations to final coherent references before Scope admission | Final Scenario Scope is the returned S1; consumers retain their own admitted SD |
| Per-request selection | Normalize ProfileRequest, ProjectRequest and BoundSelection, keeping returned values | All later acquisition and C fields use those returned values, never raw arguments |

Scenario's Library SD and Engine's Library SD may be different normalized wrappers.
Corroborate their actual Core provider/publication/source, family and semantic revision,
expected operation and binding associations. Do not require raw object equality across
edges, accept equal names as a join, inspect private admission tables, or invent a
second provenance registry. Within the selected normalized model graph, immediate
parent references must identify the actual checked predecessor as required by I2.
If Core cannot carry a necessary association, repair that real boundary or refuse.

POO ObjectContract/Function and existing receiver/reference machinery own value
validation. Core owns contextual admission and source/load provenance. Scenario owns
domain binding, expected acquisition and capture semantics. Receiver rebinding does
not rewrite lexical captures: factory functions which closed over predecessors must
be reconstructed through a qualified binding path before final admission, or refused.
Never copy fields or repair an already admitted Scope after the fact. Pure selection
cannot invoke repository/tool reads, hash workloads or user callbacks; mandatory
Core source guards remain part of admission.

a license to dynamically load a provider. Keep original proposal source and actual

later I4/I5 must be bounded and covered before C is issued. Inference can choose a
supported subset of that domain. It cannot load a newly discovered asset or change
tool configuration and pretend it belonged to the old C. Such expansion needs a new
selection/acquisition/C. Required duties and input units derive independently from
Library plus applicable policies and activity, not from candidate offers. LIB-C02's
responsibility conflict and LIB-C03's gaps must survive valid structural admission.
An unsupported malformed selector fails; an admitted architecture conflict is retained.

* Real project acquisition and complete input coverage
:PROPERTIES:
:CUSTOM_ID: i3-binding-acquisition
:END:

Scenario binds the expected acquisition operation through the selected real provider
and actual source/capability association. Core's source admission, POO read-route and
ordinary host file IO are different domains. None is automatically a generic atomic
repository snapshot or an authenticated user-confirmation channel. Bind an actually
supported owner capability; otherwise record the missing capability and block capture
issuance. Do not invent a Host API, wrap an arbitrary callback in a trusted name, or
add an always-true verification adapter to conceal the gap.

| Independent demanded role | Actual acquisition output / coverage | Missing or historical handling |
|---------------------------+--------------------------------------+--------------------------------|
| Confirmation and proposal | Supported original user-channel occurrence/content/subject plus proposed candidate source; actual relation between them | Org summary is an assertion unless separately corroborated; absent original confirmation stays a gap, never a fabricated transcript |
| Library and executable source | Actual admitted descriptors, bound SD/provider lineage, method/Program/catalog/mapping sources/revisions and qualified load cut | Missing or ambiguous source/load association blocks the corresponding qualified activity |
| Target Project repository | Resolved worktree/repo identity, actual revision and dirty/untracked bytes, build/package/config inputs and bounded enumeration | HEAD alone omits working changes; excluded/absent entries and alias restrictions are explicit dependencies |
| Architecture baseline | Prior root B if present, companion definitions, selected catalog assets, classification and transitive references | Missing root is a typed initial-state observation only when permitted; declaration/usage and actual/target remain distinct |
| Org and decisions | Required chapters, sections, decisions, demanded references and their bounded closure | Historical/current/missing classification retained; no latest-file heuristic or document title as content proof |
| Reference and target workload | Library reference Rust/QNT/Lean/protocol/oracle inputs separately from actual Project workload and requirements | Equal bytes may share storage but do not collapse these logical roles or source associations |
| Tool and execution envelope | Actual executable/config/environment/ABI identity and relevant limits through supported observation | Reading identity is not executing Rust/QNT/Lean/SysML or proving correctness/availability of every method |
| Assumptions and authority inputs | Causal hypotheses, premise sources/applicability, role mandates, revocations/history and uncertainty | Capture their observed content and claimed authority separately; no capture-time promotion to institutional grant or verified causal truth |

Represent each demanded unit by role, subject, occurrence, selector, expected source,
required adequacy and actual binding or typed gap. Require bounded complete traversal,
including absent files, directory membership and reference edges whose change could
alter the result. Capture stable owned bytes or a genuinely supported immutable source
domain. Define realpath/symlink/case/alias behavior and byte-to-logical-unit association;
a digest and path without actual read provenance are insufficient.

The acquisition owner must supply the supported stability interval for enumeration,
reads and closure completion; immutable inputs must remain those used downstream.
Hash-then-reopen and repeated hashing do not prove atomicity, prevent ABA or bind an
untrusted stream to the expected producer. If the owner cannot establish completeness
or stability, keep a refused acquisition attempt, or a predeclared partial/unstable
basis with explicit typed gaps where that activity permits it. A partial basis can
be genuine observation of a gap; it cannot fabricate the missing origin capability
or permit dependent evidence, publication or authorization. No unbounded retry,
auto-fetch/install or implicit second capture repairs an unstable read.

* C formation, origin, lifetime and renewed observation
:PROPERTIES:
:CUSTOM_ID: i3-binding-capture
:END:

| Phase / owner | Retained output and boundary |
|---------------+------------------------------|
| Scenario pure binding | Actual normalized BoundSelection with independent demanded inventory; no IO or C receipt |
| Expected acquisition | One bounded actual acquisition occurrence with immutable owned inputs, closure, typed gaps, limits and actual source/reader association |
| Basis Contract | Retain the normalized acquisition basis, including selected declarations, semantic revisions, policies, actual method/Program/assets and complete units; do not attest raw then silently normalize meaning |
| Expected origin verification | Actual expected operation verifies this basis/source occurrence under the supported verifier/clock/lifetime policy; origin receipt is outside its own snapshot |
| Final C Contract and issuance | Retain normalized returned C only if it preserves the attested basis and actual origin association; wrapper changes require qualified equivalence, otherwise refuse/reverify at the real owner |
| Current use | Fresh trusted current observation of original source/capability/lifetime conditions references original C; retain findings/expiry/revocation separately |

The source-observed Core =contribution/verification.ss= provides private adapter,
receipt and admission recognition. Its verify operation checks a snapshot before and
after an operation returning exactly true, and receipts have an issued/expiry interval.
Receipt validity uses supplied time, revocation and snapshot agreement. Admission
records a supplied-time view. These mechanisms are useful generic primitives; they
do not establish a trusted clock, an expected repository reader or an immutable
multi-file acquisition. A host caller can create an adapter with an always-true
operation. Recognition is meaningful here only with the independently expected
Scenario operation and actual source/capability association. A fresh admission view
at an old supplied time does not renew validity. No extra issuer registry is proposed.

C's owned semantic projection covers all meaning-bearing fields, typed distinctions,
ordered traces versus sets, subject/selection associations, gaps and bounds. It excludes
the origin receipt from its own attested snapshot. Opaque Function/issued objects keep
actual recognition outside canonical bytes; JSON/digest equality does not serialize
authority. Final normalization must not detach a receipt, replace a parent/method
binding or lose negative-input coverage. Failed final admission retains the real
attempt/issuance outcome without inventing rollback of an already issued receipt.

Expiry, revocation, a changed premise or source, lost process-local recognition and
unsupported recovery block current reliance. A current observation does not mutate
C, advance its issue time or become reacquisition under the same identity. Supported
reverification links original provenance and a new observation without asserting the
old receipt is renewed. Actual reacquisition issues a distinct C. Separate the
currentness of admitted Scope sources from Project bytes and the applicability of
causal assumptions: one passing domain cannot stand in for another. Applicability
change remains an explicit input to later evidence/review/decision/use invalidation,
not a capture-time proof that a causal hypothesis is true.

I4 retains all candidates, conflicts, gaps, invalidations and independently required
obligations, binds actual Program/full source batches (including empty inputs), and
creates a recognized accepted view only through its actual adoption/finalization

actual candidate validation. I6 owns the separate explicit effect request B -> O
with stable support inputs and recovery semantics. These are downstream interfaces,
not permission for I3 to run them or to add O to original C. New analysis of O obtains
new C. Aitia consumes later determinate views and performs independent checks;
Profile choice and C origin confer no review, decision or delivery authority.

actual load, cold issuance and original-provenance recovery are separate obligations;

Evidence products are the actual source/load cut, selected normalized graph and
requests, independent required-unit inventory, acquisition occurrence/owned bytes/
closure and gaps, expected origin and lifetime observations, normalized C association,
and exact lane/control outcomes. Org organizes and cites those products; D2 displays
the boundaries. Neither is another version source or authoritative capture manifest.
This chapter publishes only their design and acceptance requirements.

Open exits remain: reviewed immutable compatible upstream tuple and I0 migrated test
routes; actual I1 normalization/receiver/native source/cold/recovery qualification;
I2 missing source-authored policy/model/method/catalog/mapping assets/revisions and
bindings; concrete expected original user-input channel; qualified bounded stable
repository/closure acquisition and trusted time/currentness owner; final C normalized
basis-to-receipt recognition; supported original-C recovery (distinct from new cold
issuance). No supplied digest, name, boolean or extra registry closes these gaps.

Correctness requires honest declared selection, complete supported acquisition,
immutable same-C associations and conservative refusal/invalidation. Whether ASCENT
improves Agent proposals, architecture coverage, causal reasoning or reuse is a
separate research hypothesis requiring matched comparisons after correctness closes.
No such advantage is established by this document or by LIB-C01--C03 fixtures.
