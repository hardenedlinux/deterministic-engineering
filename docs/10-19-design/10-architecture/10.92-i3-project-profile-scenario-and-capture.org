* Scope, invariant and execution boundary
:PROPERTIES:
:CUSTOM_ID: i3-scope
:END:

I3 unifies the existing declared Project entry, effective domain Profile, typed
Scenario bindings and real project acquisition into one original capture C per
accepted acquisition occurrence. It consumes I1's normalized Scopes and I2's actual
published definitions/operations. It does not infer missing source authority from
fields or implement another dependency resolver, snapshot service or workflow engine.

#+begin_example
Declared Project providers -> Core checked K1 / provider S1 / consumer SD
 -> checked Scenario Config + actual Library/Engine and selected domain Scopes
 -> normalized Profile/request/parameters -> bound selection + independent demand
 -> actual supported acquisition -> normalized owned basis -> genuine origin -> C
 -> inputs(C), run(C), render(C/view/plan request) consume that same original C
#+end_example

Scopes and bound Program/operation definitions precede C. Results, current-use checks,
inference views and generated models remain separately associated outputs; they are
not appended into the basis that acquired them. Unique C means one actual captured
basis for a declared comparison/run, not a global singleton or exactly-once IO claim.

This update changes Org/D2 only. No implementation, model, package, input acquisition,
clock/tool invocation, inference, build/load/cold/recovery, acceptance, publication
or orchestration is executed. I0/I1/I2 implementation/qualification remains open;
this plan creates no real C, origin receipt, evidence, review or delivery authority.

A route with a declared required Domain must resolve it even for a Generic choice.
It cannot prune a failing edge, import raw Config as fallback or pretend it selected
a narrower publication. A genuinely narrower route has its own declared dependency
set and can share pure helpers. Preserve lazy unrelated siblings and reader/test
bootstrap; choosing a domain Profile must not force every available Module.

Core profile/extends settings and the domain LibraryFormationProfile have distinct
roles. The domain Profile chooses only supported offerings from already admitted
providers. It cannot resolve arbitrary packages or mutate the provider graph. Config
fixes the existing Scenario identity/purpose and supported input/acquisition policy,
not an independent Profile registry or a caller-selected validator.

Scenario's Library edge and Engine's Library edge can have different normalized SD
wrappers. Corroborate their actual admitted subject, source/publication/family/
semantic revision and method binding through supported Core/I2 associations, not
raw eq? across edges or matching printed names. Within a normalized exported model
graph, immediate parents still point to its actual checked predecessors. Do not
rebuild Generic/Integration from source objects to force pointer equality.

Source lineage must arrive from the expected actual Core/provider binding, not a
request-supplied record. Existing selected records/dependency evidence and admitted
operation/source associations are the supported owner boundaries to qualify. The
existing opt-in export binding protocol is not a universal Scenario capture issuer.
If the selected interfaces cannot carry the association needed for a full join,
refuse that route and repair the owner boundary; no private-table inspection,
application provenance registry or new generic binding hook is justified.

The generation read remains Scope -> trusted expected role/family association ->
LibraryDeclarationContract V1 in organization Types. Profile/selection/C can retain
that reference, but cannot copy or choose a new version field. Project revision,
semantic revision, source/build/load cut and clock interval stay distinct.

Policy selection is applicability, not adoption or authorization. Required actual
mandate/roles/classification/history inputs are acquired separately, marked absent
or unverified when unsupported, and never filled from a coding-policy fixture.
A user-confirmed design goal is not an institutional grant or review disposition.

Well-formed LIB-C02 conflict and LIB-C03 omissions remain candidate data for later
ASCENT. Reject malformed/unsupported selection, not legitimate conflicting proposals.
Independent required units derive from definitions/policies/parameters/operation and
all supported candidate/plan applicability before comparing offered allocations.
Proposals cannot erase a requirement by omitting it. Incompatible selections need
separate captures or an explicitly supported common footprint, not an undocumented
merge of unrelated results under one C.

* Real project acquisition, coverage and stability
:PROPERTIES:
:CUSTOM_ID: i3-acquisition
:END:

Scenario's bound operation invokes actual qualified readers. An owner implementation
may use explicitly source-bound operations or typed Module capabilities where
published; it cannot invent a Host API or accept caller callbacks to fill gaps.
Core Module SourceRef, POO issued slot reads and verification adapters cover their
actual domains, not arbitrary repository/OS/tool IO. Unsupported mandatory acquisition
or origin capability blocks full capture.

| Logical input role | Required DE-CASE-01 observation / retained source |
|--------------------+--------------------------------------------------|
| Confirmed intent and proposal set | Actual available confirmation/proposal content, source occurrence and supported acquisition channel; authored Org/Profile accounts are claims if the original channel is unavailable |
| Library/operations/selection | Actual normalized definitions/parent/policy/catalog/method/Program association, semantic revisions, selected source bytes/build/load observations or explicit qualification gaps from I0/I1 |
| Project implementation | Real repo/worktree identity, observed HEAD plus included dirty/untracked bytes, selected source/package/config/build inputs and include/exclusion/enumeration/negative dependencies. Equal HEAD is insufficient |
| Architecture and model baseline | Actual project.sysml and selected companion/catalog/resource bytes, element selectors, current/target classifications and reference closure. Future generated root bytes are not inputs of this C |
| Org/products/decisions | Required product/section/decision selectors derived from selected obligations, observed bytes/references and current/historical/missing/conflicting classification; no hardcoded complete-doc inventory owned by Scenario |
| Library reference workload | Selected six-case crate/lock/oracle/model/protocol and intended bounded claim domain, distinct from target project implementation even when paths/bytes overlap |
| Tool and environment inputs | Supported observations of actual selected executable/ABI/resources/config/environment and declared limits; reading identity grants no execution/build/install/fetch permission or verification result |
| Premise/causal/adoption/history | Required model/causal/applicability/data/measurement/transport/role/mandate/history inputs or explicit missing/unverified claims; capture proves acquisition, not premise truth or grant validity |

For each independently demanded unit retain role/subject/occurrence, selector,
expected source/adequacy and observed binding or permitted typed gap. Missing trusted
origin is different from genuinely observing a missing document. A complete route
requires every mandatory unit and qualified acquisition; a preselected partial
variant can preserve recognized gaps but cannot claim full readiness. Do not switch
to partial after the complete route fails.

Readers retain owned immutable bytes or a supported immutable source domain, exact
base/realpath/alias/symlink rules and original-to-staging association. Capture content,
enumeration and negative observations as required; include links/imports/resources
and environment/ancestor configs actually relevant to the selected method. A changed
symlink, directory member, missing-file appearance or dirty source during acquisition
cannot be hidden by an unchanged commit or path hash.

Use the actual owner's supported stability guards over the acquisition interval.
Repeated hashes alone do not establish a universal atomic snapshot or ABA absence.
If inputs cannot be acquired stably within the declared limits, refuse or retain an
explicit unstable gap only in a permitted partial variant. A new acquisition attempt
has its own occurrence; retain failed attempts rather than combining old metadata
and new bytes into one invented stable basis. There is no autonomous unbounded retry.

Library/reference/project roles may share physical bytes in this self-hosted case.
Deduplicated storage must preserve separate subject/demand/provenance meaning. Run
and render consume captured immutable data; they do not hash then reopen mutable
paths. Live checks compare their independently observed current conditions to that
basis without replacing its original bytes.

* Normalized basis, original origin and unique C
:PROPERTIES:
:CUSTOM_ID: i3-capture
:END:

| Stage / actual owner | Target retained fields or result |
|----------------------+----------------------------------|
| Actual acquisition occurrence / Scenario operation | Owner-created occurrence-ref, expected operation/source-generation, actual bound selection/request, attempts/read outputs/limits and producer associations. Caller request IDs/digests do not create this identity |
| Owned normalized basis / expected Scenario Types | Occurrence, checked selection/Profile/parameter, actual Scope/parent/policy/model/method/catalog/Program/mapping refs, intent/candidates/plans, required units, observed immutable inputs/gaps/source cut/limits and acquisition associations |
| Origin assertion / actual expected operation | Exact basis/occurrence and recognized reader/selection/source association under declared stability limits. It asserts this acquisition, not architecture correctness, successful model validation or true causal premises |
| Original origin association / actual Core adapter and trusted Host | Exact independently expected adapter/operation/source, real receipt/interval and trusted clock/lease policy, bound to retained original acquisition. No arbitrary adapter name or public boolean supplies trust |
| Final C / Scenario admission | Checked immutable basis plus actual original origin association and supported lifetime/use limits. Preserve attested meaning; failure returns distinct refusal/draft, never a partially recognized C |
| Current-origin use / later operation | Fresh target/check/time/conditions and same original C/basis/occurrence/origin; separate verification observations as supported. No edit of original C, receipt times or sealed inputs |

Use normalize basis -> actual recognized origin verification -> retain genuine origin
-> final C admission. Receipt is outside its own basis snapshot. Final normalization
must not change already-attested meaning; if it does, refuse/reverify at the owner,
not patch the receipt or reconstruct a matching receiver. The same actual C and
origin association are retained by same-process consumers; an equal copied record
is not evidence of producer ownership.

Frozen semantic input and opaque operational bindings are distinct. Basis
canonicalization includes meaning-changing identity/revision/role/gap/limit and
actual source associations, preserves ordered traces versus declared sets and
symbol/string distinctions, and retains normalized parameter/definition meaning.
Do not serialize closures, drop their footprint because JSON cannot encode them,
or pretend a mutable Scope's future slot cache is immutable input. Opaque actual
operations/issued tokens retain owner recognition and live guards outside the
canonical byte projection. Any unsupported binding that cannot be related to the
basis is an explicit capture gap/refusal, not an invented portable credential.

Current Core contribution/verification.ss exposes yuanxu-verification-adapter,
yuanxu-verify, yuanxu-verification-valid?, yuanxu-verification-admission,
yuanxu-verification-admission-valid? and revoke. It privately associates the actual
adapter/receipt/snapshot/interval, copies snapshot strings and checks pre/post
snapshot equality around operation returning exactly #t. Interval is
[issued-at,expires-at), with nonnegative integer bounds and issued-at < expires-at.
These existing mechanisms do not provide an arbitrary-repo capture service.

The Scenario must independently bind the expected real producer operation, source
and acquisition domain. Anyone can create a trivial adapter; generic registration,
matching identity or successful valid? alone does not prove project IO truth.
Trusted owner supplies actual clock/lease policy; submitted now/until values are
not a trusted clock. An admission object indexes its supplied fixed instant, not
continuous time; a later operation must check actual current time and conditions.

Capture failures after actual issuance retain attempt/receipt diagnostics at their
owner; issuance is not claimed rolled back. A recognized missing-content acquisition
may form a valid gap-bearing C only under its declared variant. An unavailable
reader, unrecognized acquisition or fabricated/copied receipt cannot.

Expiry/revocation/process loss does not renew C by changing a timestamp. Supported
re-verification can retain the original occurrence only if unchanged meaning and
original retained provenance are genuinely checkable; it creates a new observation/
receipt, not an edited original. Reacquiring project content creates a new C even
when bytes match. Build restoration, JSON/hashes or restored model files cannot
reconstruct private origin issuance; unsupported same-C continuation remains open.
