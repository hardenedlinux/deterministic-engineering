* DESIGN Purpose, terminology and scope
:PROPERTIES:
:CUSTOM_ID: library-types-and-contracts
:STATUS: WP01 field/file/validation design; no implementation or test execution
:END:

This document specifies WP01 of 10.41 at existing file, field, inheritance and
validation boundaries. The implementation uses the existing POO Type protocol,
ObjectContract, Function Types and Core contextual/publication Contracts. These
are the actual mechanisms; there is no separate category of Library described
by the adjective /native/. That word previously mixed three distinct facts:
using POO/Core mechanisms, checking prototype ancestry, and running compiled
code. From here on, name each fact directly.

Public design/file names describe responsibility: Library Types, declarations,
Contract validation, publication, compiled loading or Rust observation. Proposed
API names use the same rule. An upstream identifier such as
PooFlowNativeObjectContract is quoted unchanged only when referring to that exact
existing API. Existing source symbols, compiled/source-loading observations and
historical schema tokens retain their traceable identities until a qualified
implementation migration. The adjective is not a quality grade or a new layer.

The maintained 10.35/10.36/10.37/10.41 design filenames and 90.99 paired view are
renamed by responsibility in this documentation task. Numbered IDs and existing
CUSTOM_ID anchors remain stable. Current links are updated; historical evidence
catalog entries, saved execution records and implementation paths are unchanged.

WP01 defines expected Types, declaration metadata and admission boundaries. WP02
constructs/publishes the changed objects; WP03 binds/captures their use; WP04-WP09
implement evidence/query/review/delivery associations. Their field/signature
requirements are allocated below without claiming those downstream operations
already exist or supplying permissive placeholder Contracts.

* SPECIFIED One generation owner and descriptor association
:PROPERTIES:
:CUSTOM_ID: library-contract-version-owner
:END:

| Subject | Required design |
|---------+-----------------|
| Sole owner | BackpressureDeclarationContract in abstract/types.ss, an ordinary Core Contract descriptor with stable identity backpressure-memory/declaration |
| contract-version | One authored field on that descriptor. Target value is the symbol V1; it is not parsed from a namespace, revision, filename or Org property |
| Generic role Contract | BackpressureModelContract; stable identity backpressure-memory/model |
| Rust role Contract | RustResourceModelContract; stable identity rust-resources/model |
| Integration role Contract | BackpressureIntegrationContract; stable identity rust-resources/integration |
| Policy role Contracts | BackpressureReviewPolicyContract retains bounded coding-method meaning; BackpressureDesignReviewPolicyContract is the distinct WP05 design-review sibling under the same family owner |
| Each role descriptor | declaration-contract refers to that same admitted family owner; value-contract is its complete effective ObjectContract; identity and role identify the expected role. It has no separate contract-version field |
| Each semantic definition | contract refers to its actual admitted expected role descriptor. identity/revision identify engineering meaning; parent identifies immediate engineering ancestry or false |

The role descriptor metadata is explicit: identity is its stable Contract symbol;
role is one of generic-model, rust-model, integration or review-policy;
declaration-contract is the admitted family reference; value-contract is the
effective ObjectContract. Existing Core classify/admit/obligation methods remain
Core's protocol, and pure domain relation checks compose through that protocol.
There is no separate role version, descriptor revision counter or per-field
responsibility mirror. Shared model-shape bindings contain no concrete role ID.

The read is selected scope -> selected role Contract -> declaration-contract ->
contract-version. Scope.declaration-contract and definition.contract must agree
with those admitted references. A role reads the shared value through that path;
it does not copy it into its own metadata or inherit a flat version slot by
subclassing the family descriptor. Role Contracts compose the family reference
and shared value shape while deriving their Core behavior from PooFlowContract.

The generation literal is authored once. Validators compare actual owner/source/
role association and the admitted owner value; they do not keep another literal
in each role, Profile, interface or document. The supported owner is pinned by
the expected source-qualified descriptor association and its guarded reads. A
runtime mutation of that descriptor, including changing and restoring a slot,
is not authorized merely because it still has the same object identity or V1
label. Existing Core object/read revisions and source-currentness mechanisms
must detect the changed association and require fresh admission. No second
version counter, signing service or writable supported-version registry is added.

An untrusted candidate's contract/declaration-contract fields are treated as
references, not instructions to invoke that candidate's Type methods. Resolve
the expected descriptor from the trusted required scope first. Reject substitution
before executing a claimed validator. Across processes, pointer equality does
not establish continuity: re-admit the provider/descriptor/source closure before
reading generation and binding definitions. A serialized descriptor is not an
executable trusted Contract.

The semantic tokens ownership-budget/v1, backpressure/v3 and
backpressure-integration/v1 remain opaque current baselines. They are not changed
or interpreted as V1/V3 generations here. Review policy revision remains its own
meaning baseline. Source/content/object revisions and tool/schema versions keep
their respective purposes.

* SPECIFIED Value inheritance and role constraints
:PROPERTIES:
:CUSTOM_ID: library-contract-inheritance
:END:

Three relationships must be kept distinct:

| Relationship | Target graph and rule |
|--------------+-----------------------|
| Value-shape inheritance | Common declaration fields -> shared model shape -> Rust model shape -> integration shape. Policy shape derives from common declaration fields as a sibling of model shape |
| Expected role constraints | Generic, Rust, integration and policy each compose the appropriate effective shape with their own identity/parent/applicability constraints. Rust does not refine a generic-role identity constraint; integration does not refine a Rust-role fixed identity/parent constraint |
| Engineering definition inheritance | Generic has no parent; Rust has actual admitted Generic parent; integration has actual admitted Rust parent. Policy has no model parent and composes with applicable model roles |

Shared value shapes need no additional public manager or registry. Their names
are implementation-local POO ObjectContract bindings in the Types files; public
consumers receive the expected role/scope/parameter Contracts. Shared field maps
are extended into the complete effective role before validation, including
extra-field rejection. Never validate a full Rust value with an unextended
header that rejects every Rust-specific field, and never allow arbitrary extras
to hide that mistake.

The shared family descriptor may refer to the common value protocol; concrete
role admission always uses the role's full effective shape. Role descriptors
reference that family rather than inherit its contract-version field. Their
Core contextual behavior uses value-contract, classification and pure obligations;
ordinary field Types are not duplicated in Core responsibilities. Contextual
responsibilities are for real contextual child admissions.

POO ObjectContract constraints/refine preserve inherited checks and operate on
the checked value. Derived effective maps remain receiver-local after a parent
map has already been forced. POO Function Types wrap calls when validated; the
returned wrapped value is the one to publish/use. A structural membership check
or diagnose call is not a substitute for validate and its returned value.

Actual prototype ancestry is checked only where a declaration explicitly promises
it, using POO required-prototype or the existing Core prototype-aware Contract.
Shape reuse does not fabricate such ancestry. Contextual parent-reference checks
still bind the actual admitted engineering parent even when a compatible value
has been normalized into a checked receiver. Proven ancestry alone establishes
neither trusted source origin nor semantic refinement.

* SPECIFIED Declaration fields and row Types
:PROPERTIES:
:CUSTOM_ID: library-declaration-fields
:END:

All declared fields below are required for their effective role. An empty value
is allowed only when explicitly meaningful, such as root parent=false. Missing
fields are not replaced by defaults invented by the validator. Exact field names
below are target responsibilities, not code already added to the current files.

| Field group / owning Types file | Shape and relational boundary |
|--------------------------------+-------------------------------|
| Common: identity | Symbol; one typed identity binding for each concrete subject, referenced by object construction and its expected role constraint. No repeated independent identity literals/registry |
| Common: revision | Nonempty semantic baseline text; actual content/source identity remains independently captured. No lexical ordering or suffix parsing |
| Common: contract | Opaque descriptor reference whose association must equal the expected admitted role; no arbitrary candidate-supplied validator invocation |
| Common: parent | Explicit false or declaration reference at common shape level; concrete role checks narrow it to false, actual Generic or actual Rust as applicable. No cycle, foreign provider or skipped ancestor |
| Shared model: lifecycle | Unique nonempty list of state symbols with declared state meanings; shared shape does not fix the generic-only vocabulary |
| Shared model: rules | List of three-symbol factor/obligation/method rows, retaining current responsibility. Obligation IDs unique in the effective model; inherited duties preserved; method identifiers resolve to declared capability meaning |
| Shared model: dependencies | Unique obligation/input-role pairs; every obligation belongs to rules and required input roles are complete for that declaration. Extra/dangling/contradictory mappings refused; no requirement disappears because no result exists |
| Shared model: assumptions | Typed premise records with identity, statement/reference and affected duty/subject links. Required lifecycle/ownership/model bounds are explicit; presence of text does not prove the premise |
| Shared model: assets | Typed formal/model/source references with identity, purpose, location/reference and affected duties. Files are not read/executed at declaration construction; capture/observers establish actual bytes and meaning later |
| Shared model: capabilities | Typed method definitions with identity, claim/duty scope, supported parameter/domain/mode and required input/result roles. Semantic declaration remains distinct from availability of an actual callable |
| Shared model: qualification | Explicit declared evidence-strength/limit value retaining the current conditional/model/specialization distinction; no approved? or complete? flag inferred from it |
| Rust addition: state-map | Unique declared child-state/parent-state mapping with both endpoints in the respective lifecycle; every required projected state accounted for. Direction is explicit, avoiding reinterpretation of today's active->cpu-running notation as its inverse |
| Rust addition: runtime-premises | Typed ownership/scheduler/payload/inventory/panic/workload premise references linked to assumptions and duties; actual runtime/source/tool observations belong to capture/methods |
| Rust existing design / trajectories | Retained only as declared nonempty design reference / list of references in the effective Rust shape; documentation links cannot discharge duties |
| Integration addition: case-links | Exactly one RL/SI/TM triple for each M01-M06, linked to effective rules/capabilities with no duplicate, unknown or missing case. Retain M06's property-counter/control distinction |
| Integration addition: mapping | Identity, semantic revision/reference, input/output domain, projection losses and affected duties as one typed definition; correspondence.ss consumes this definition |
| Integration addition: deltas | Typed changes to parent assumptions/model transitions, with rationale, supported mode and verification-duty links. Queued cancellation is explicit; declaring a delta is not proof it preserves all base properties |
| Policy addition: applies-to | Nonempty typed associations of stable model identity and expected role descriptor, plus supported purpose/scope. Only source-admitted roles in the selected family can match; policy applicability is not project adoption |
| Policy addition: criteria | Unique criterion/duty records with required method/evidence/product roles, semantic strength and explicit pending/counter/conflict/unsupported handling. Real adopted standards may be referenced; no fabricated NASA clauses |
| Policy addition: products / responsibilities | Reusable product-role and responsibility requirements, including required document/decision/trace content, allowed selections, approval coverage/independence and authorized exception constraints. No people, signing paths or project grants |
| Policy addition: reconsideration | Required history categories, repair/denial/supersession/withdrawal triggers and current-use conditions linked to criteria. Actual discovery, authority acts and revocation remain Aitia/project operations |

Nested row/premise/reference/capability/policy values use POO Types and pure
relation constraints in the same existing Types roles. They are not JSON Schemas
or a second public grammar. No table here authorizes untyped arbitrary objects,
callbacks, raw scope extras or generic Any fallbacks in an advertised checked API.
Exact capture identities, timestamps, actual tools/results, project revisions,
reviewers, approved dispositions and signature material do not belong in these
reusable Library definitions.

For the current Rust lifecycle, the complete target projection is waiting ->
waiting, queued -> queued, cpu-running -> active, result-pending -> returned,
cleanup -> cleanup and released -> released. Shared-state identities are explicit
rather than guessed from absent rows. Integration retains that engineering map;
its observation/QNT mapping separately declares running/done vocabulary and the
queued-cancellation extension, so those distinct domains are not conflated.

The target state-map convention is child -> parent. Current pairs active ->
cpu-running and returned -> result-pending are migrated deliberately to the
opposite order with both endpoint meanings preserved, not silently copied under
a new convention. Mapping coverage/refinement still needs its semantic obligations;
endpoint validity alone is insufficient.

These parameter and Context names supersede the earlier proposed API names in
10.37/10.38 for the target refactor and are direct migrations for active callers. Existing source identifiers are unchanged in this task. There is no
permanent pair of old/new Contract APIs or alias fields. Context construction and

as if it implemented that future contract. Its current baseline can remain
explicitly unqualified until the dependent migration is ready.

| Callable boundary | Expected typed input/output association | Phase and limit |
|-------------------+-----------------------------------------+-----------------|
| Published generic methods | Applicable generic parameters or captured generic use, declared request/domain -> method-specific result | Validate/wrap through actual POO Function Types; unsupported method remains unavailable rather than a procedure-shaped stub |
| Published Rust/integration methods | Appropriate C and bounded application request/qualified upstream observations -> scoped result | Typed signature plus actual C/source/issuer checks from WP03/WP04; no root/Profile/tools passed beside C to override capture |
| Currentness / result-use operations | Actual captured/result/use value expected by its real owner -> validated use or refusal | Keep producer-owned private issuance. A Type checking a presentation cannot manufacture resource-result or establish original execution |
| Scenario evidence/review operations | Same C plus actual issued uses/identified Q/real review inputs -> identified inference/prepared review association | Scenario/Aitia own these downstream operations. Structural function wrapping is not review/decision authority |

Method-contracts is an ordinary typed publication value bound to actual methods,
not a validator-selection registry. The trusted publication supplies expected
Function Types; candidate functions or attached labels cannot choose their own
signatures. Validation wraps without invoking method bodies/defaults. At actual
call time, supplied arguments and returned value count/types are checked and
body/default exceptions propagate. If a result Type needs the private producer's
recognizer, bind it at that trusted implementation/publication boundary; Types
must not import methods back or claim a public shape authenticates issuance.

* SPECIFIED Validation order, trust and extension boundaries
:PROPERTIES:
:CUSTOM_ID: library-contract-validation-boundaries
:END:

| Boundary | Required action / retained value | Refusal or remaining obligation |
|----------+----------------------------------+----------------------------------|
| Descriptor definition | Build expected Types from POO/Core and typed domain bindings in acyclic source roles; validate Type descriptors as developer-owned definitions | Malformed expected descriptor is a definition error, not a reason to execute a candidate's replacement validator |
| Required scope admission | Core source/publication checks choose the actual expected scope and required Parent | Foreign provider/role/family or changed source association refused; equal labels/shape alone insufficient |
| Effective value validation | Check prototype if explicitly required; declared shape/field Types; wrap/normalize fields; run inherited and role relation checks on the returned value | Missing/unknown/type-invalid fields and conflicting relationships refused with field/relation diagnostics. Unknown fields can be rejected without demanding their getters |
| Contextual association | Check expected descriptor reference, family owner, actual immediate parent/provider and applicability against the admitted required scope | No parent cycle/skipping/substitution or policy-model inheritance. Classification/constraints remain pure; they do not run external methods |
| Publish/read | Publish the checked definitions/functions and their associated expected descriptors; generation read follows the sole owner path | Do not discard validate's normalized/wrapped result. Stable labels cannot bypass descriptor/read revision/currentness guards |
| Scenario selection/capture | Bind actual selected leaf/ancestors/policy, validate parameters/domain and acquire input closure under 10.38 | Field admission does not establish captured source truth, atomic acquisition, issuer identity or project authority |
| Semantic/evidence/review use | Apply method/content/refinement/history/authority duties under 10.39/10.40 | Contract success is not a behavioral proof, completed method, reviewer appointment or delivery approval |

Do not duplicate one field-Type map in ObjectContract and Core contextual
responsibilities. Do not append replacement obligations that discard inherited
ones, run the candidate's classifier before association checks, cache accepted
booleans independently of the actual source/read basis, or normalize a contextual
child into a detached substitute for the parent's already checked child.

POO/Core validation is not a sandbox for arbitrary Scheme getters/callbacks.
Declared getters and pure constraints execute under the selected source/read
boundaries; arbitrary external reads remain open/unsupported premises rather
than silently assumed pure. Capability publication is deferred: loading/admitting
Library declarations must not invoke Rust, QNT, Lean, SysML or Aitia authority acts.

The consolidated WP01 target includes the later WP05 design-policy descriptor
and exact Scope fields above. Both policies have role review-policy and the same
family owner, but different fixed subject identities, semantic revisions and
applicability; they do not inherit each other's fixed-identity Contract. Content
operations extend the existing methods/method-contracts associations with explicit
supported capability keys and expected Function Types, not a second dispatcher.
CT01/CT04/CT10/CT12/CT13 apply to both policies at their actual scopes; a bounded
policy cannot silently substitute for design review. See [[file:10.52-contract-consistency-and-implementation-order.org::#consistency-findings][the whole-chain audit]].

WP01 is accepted only when the actual implementation demonstrates CT01-CT15 at
its declared scope, with exact source/compiled identities, diagnostics and
side-effect controls. Declaration/type tests and downstream integration checks
are separate evidence. Historical cold-loading/recovery failures from 10.41 stay
open until their actual current acceptance passes; completing WP01 does not close
WP00 or WP10. Test ownership follows the existing Library/type/selection tests,
with existing POO/Core controls reused and only domain-specific cross-boundary
controls added where needed.

* SPECIFIED Implementation sequence and status
:PROPERTIES:
:CUSTOM_ID: library-contract-design-status
:END:

First define shared value/row Types and the single family descriptor in abstract
Types. Then define generic shape/role/parameters and Rust/integration/policy shapes
and role constraints without object imports. Define parameter/callable/scope
expectations under those trusted descriptors and test effective-field/normalization/
reference controls. WP02 then migrates object construction, semantic catalogs and
publication together; WP03/WP04 supply capture/method-dependent boundaries before
their corresponding APIs are claimed usable. Active callers migrate directly;
there is no intermediate permissive publication or duplicate live API path.

This details GA01/GA03/GA04 and the WP01-facing parts of GA02/GA05-GA13/GA18 from
10.41. It preserves DE-R01/R03 and DE-T01; model/content/refinement and review
obligations remain allocated to their later owners. Source-grounded terminology
and filenames replace the ambiguous adjective; no upstream API, implementation
path, historical schema/version or execution receipt is renamed here.
