* DESIGN WP07 objective and authority boundary
:PROPERTIES:
:CUSTOM_ID: aitia-review-adaptation
:STATUS: Target file/field/call/receipt design only; no implementation, verification or review submission
:END:

WP07 consumes one acquired C and its actual determinate Q, prepares an identified
review basis R, separately verifies context and content, and assesses the selected
technical review requirements with every pending/counter/conflict preserved.
It binds actual Library policy, project revision/scope, role/grant and product
associations. It does not appoint reviewers, adopt a policy, decide exceptions,
submit a review or create a release/delivery permission.

Library owns policy/criterion/coverage meaning; Profile selects supported options;
Scenario supplies the same C/Q and project bindings through trusted operations.
Aitia owns common review semantics and verification adaptation; Core's existing
verification boundary owns local receipt issuance. ASCENT Session remains the
fact/evaluation owner. WP08 owns full history/disposition/reassessment authority,
WP09 recipient delivery/use and WP10 joint qualification. None is replaced by a
new local approval engine, receipt registry or an Org schema.

R is an inert, inspectable binding until actual operations occur. A verified
inventory or negative finding is not a positive adequacy result; technical
eligibility to proceed is not a decision. Current source/compiled/cold/recovery,
policy-adoption and actual role gaps remain open.

Extend SdlcVerificationRequest's supported purpose enum at its actual owner with

submitted purpose/classifier fields cannot route validation. Existing standard/
authority constructors and snapshots still explicitly accept only their actual
supported purposes, and source/compiled controls must cover the changed base.

The common snapshot includes exact R identity/basis, project/revision/scope,
policy/Contract/source association, selected verifier operation/trust boundary,
purpose/assertion, criterion/subject and complete required fact references/
conclusions/limits. Own strings/collections and use a qualified typed encoding;
no lossy symbol/string conversion, hidden mutable POO state or omitted semantic
fields. Facts are snapshotted as data; snapshots are not a hook for tool execution.
An excluded field cannot be allowed to change what a verified request means.

R's basis is finalized from identified C/Q/policy/project/product/role/prior input
references before verification requests exist. Requests reference that basis and
their own assertion facts. Later receipts, assessment, reviewer deliberations and
assembled dossier are outputs/envelopes bound to it; they are not inserted into
their own input digest. The old 10.34 draft can be a C input; it does not become
an issued request just because its path is listed. C and Q are never amended to
contain their future R/receipt outputs.

The qualified verifier operation is bound from the admitted Aitia/Scenario host
source and selected policy capability, not supplied in request fields. Low-level
Core APIs remain available to their rightful callers; their mere use does not
make an arbitrary always-true callback the project's trusted verifier.

Use known actual import/loaded source and compatible compiled artifacts; package
version or a filename alone does not identify the executed checker. Existing
Assurance Host can supply its genuine subject/input/currentness support where
its declared mapping fits. An actual source-bound support review still leaves
semantic independence/conformance/approval open as its API states. A Q is not
re-encoded into a second live assurance fact store to bypass this boundary.

Requests and facts may be public presentations; the owner resolves its actual
expected R/request/purpose and verifier internally. A caller cannot route an
unknown object to a favorable verifier by changing purpose, issuer or checked?.
Private issuance/source associations are never reconstructed from serialized R,
Q/W, signatures, cached receipts or a report with qualified=true.

* SPECIFIED Independent context and content verification
:PROPERTIES:
:CUSTOM_ID: aitia-independent-context-content
:END:

| Verification purpose | Exact question and inputs | Does not establish |
|----------------------+---------------------------+--------------------|
| review-context | Is this project occurrence/revision/scope actually bound to the selected applicable adopted policy/Library/parent/Contract/purpose, with the required authentic roles/mandate/status at the declared cut? | Architecture truth, semantic content adequacy, all product closure or final approval |
| review-content-inventory | Does the exact required/actual product/criterion/evidence inventory, with gaps explicitly accounted for, faithfully bind R to C/Q and accessible qualified references? | Fulfillment of missing roles/products/criteria, rationale adequacy, method re-execution or whole-case success |
| review-content-criterion | Is this precise assertion/conclusion on this product/claim, domain and basis established by the actual qualified content/evidence/semantic findings under the selected criterion? | Broader property, a different criterion, current appointment, exception or disposition authority |

Context verification checks actual project/revision/source identity including the
dirty-worktree/input basis, not only HEAD or a human revision label. It checks
authentic policy adoption/applicability and grants for the exact operation/scope,
with validity/status/trusted source coverage. A policy object describes required
roles; it cannot appoint principals. A public self-declared role, author signature
or the user's permission to draft does not establish a standing semantic-review
or disposition appointment. Mandatory unresolved roles prevent the corresponding
complete-context assertion; partial findings remain inspectable without inventing
a positive receipt. Another bounded assertion requires its own declared scope.

Content verification checks exact acquired sections/model/decision/view identities,
required closure and actual-target distinctions; complete Q/program/source/query
scope and explanation; original W/E and target U/claim/domain/strength/footprints;
historical evidence/counters; and independent semantic findings where required.
It calls the actual qualified producers/readers, not a new ambient Session query
or a success-only row/count summary. A same-run SI/TM result remains an observed
cut/path result, not full repository architecture or Rust refinement evidence.

Logical/purpose independence is mandatory: a context receipt cannot satisfy any
content purpose; an inventory receipt cannot satisfy a semantic criterion; one
criterion cannot satisfy all DE-O families. The selected policy separately defines
required verifier/reviewer independence and permitted role combinations. Distinct
function names, packages or two signatures by the same author are not independent
semantic review. C1's Agent authoring does not fill its unassigned Semantic reviewer.
Shared trusted infrastructure may be permitted without claiming independent
methodology or reviewer identity from code separation alone.

An existing WP05 semantic finding is a qualified input with its actual C/A/E/W/use
and attribution. Deliberation produced about this R is a later review output,
bound to exact R/product/criterion and actual principal; no invented shell attempt
or retroactive change to C/Q. If new evidence is meant to discharge a Q missing
unit or change its findings, it must pass WP05/WP06 and yield a new Q/R basis.
Changed product/selection/adoption/role input requires the appropriate new C.
A fresh status check on an existing grant observes current eligibility without
rewriting that original grant or proving global history completeness.

* SPECIFIED Pending, counter, conflict and assessment meaning
:PROPERTIES:
:CUSTOM_ID: aitia-review-assessment-meaning
:END:

| Situation | Required review result |
|-----------+------------------------|
| C/Q/request shape or actual producer binding invalid | Refuse the affected operation with diagnostics; no positive verification receipt or substitution of an old Q |
| Complete Q contains pending/unsupported/missing | R may faithfully prepare; retain exact mandatory duty/unit/product/reviewer gaps. A valid inventory-accounted receipt cannot make those criteria fulfilled |
| Actual scoped holds/refuted W and control success | Preserve property conclusion and control expectation separately; M06 success remains ownership counter, Lean negation remains budget counter and QNT path keeps its mapped meaning |
| Comparable support/counter both present | Retain both and conflict with their precise source/use/claim/basis. No latest-looking revision, green majority or signature resolves it |
| Different run-local subjects or content claims | Preserve distinct scopes; do not invent logical conflict or universal support. Aggregate only under actual policy coverage/comparison meaning |
| Context valid, content absent/incomplete | Retain valid context receipt at its real scope; content verification/criterion requirements stay outstanding |
| Content integrity/criterion verified, context or role absent | Preserve the actual finding; policy-required complete context/independence remains unverified. No content result appoints its reviewer |
| Required findings and fresh separate verification meet policy technical requirements | Report exact scoped technical assessment, with all retained counters/limits and authority still required. It is not an approved/released decision |
| New denial/history/role withdrawal or unresolved prior failure | Current review use is blocked/requires reassessment at the affected scope. WP08 owns actual discovery/resolution; WP07 cannot suppress it or manufacture completeness |

A receipt states that its precise request assertion was verified. It does not
necessarily state that a product is adequate. For example, inventory accounting
or an authenticated scoped refutation can be true while positive adequacy is
unestablished. The assertion, conclusion and limitations are explicit snapshot
inputs and are checked through their own expected Type/operation. Missing access,
unsupported parser or absent reviewer is not a semantic refutation; preserve
undetermined/pending as in WP05/WP06.

Required review purposes/criteria derive from selected policy, not whichever
receipts were returned. All/alternative/negative-control/correlated coverage must
match the published meaning. Partial verification cannot vanish from a table to
produce technical eligibility. A policy may demand documented evidence of an
unsafe alternative; that is not permission to change counter into support or
silently waive a positive property. Any required exception/denial resolution
needs real WP08 authority and does not rewrite the original failed property.

Keep assessment axes separate: binding conformance, context validity, inventory
accounting, per-criterion findings, independent role coverage, current evidence/
receipt/source status and remaining authority obligations. A public assessment
is explanatory data. Later authority must verify its actual source/current-use
association; it cannot accept a caller-edited technical-eligible? or admitted?.
The existing standard gates and design support reviews keep their explicit
release-authorized? false/conformance/independence exclusions.

* SPECIFIED Receipt lifetime, invalidation and replay
:PROPERTIES:
:CUSTOM_ID: aitia-review-receipt-lifetime
:END:

Core issues only after its actual selected operation returns exact #t and the
copied snapshot remains equal before/after. Its private records bind the actual
receipt object to the snapshot, issuer and interval. The interval is issued-at
inclusive and expires-at exclusive; deleting its private record revokes it.
Copying/editing a receipt presentation cannot recreate its private association.
These are local-process guarantees, not exportable signatures or truth of an
untrusted callback.

| Event / proposed use | Required target handling |
|----------------------+--------------------------|
| Same R/purpose/assertion, unchanged required basis, within policy duration | Reuse an original valid receipt only after actual fresh dependency/role/evidence/status checks and Core admission at the current trusted instant. Technical verification can be idempotently reusable; it is not a one-use action token |
| Another C/Q/project revision/scope/policy/purpose/criterion/role/product basis | Different request seal and actual expected binding; old receipt cannot answer it. Reprepare/reverify affected basis; no generation-label or same-content shortcut |
| Mutated request/receipt/adapter or foreign adapter instance | Reject actual use under expected owner and Core private identity/snapshot checks. Same issuer string or a genuine low-level adapter with a fake operation is not the selected verifier |
| Expired/not-yet-valid/revoked receipt | No current admission for that purpose. Retain history and diagnostics; only a genuine new verification can create a fresh receipt |
| Underlying file/W/use/checker/policy/grant/status changed while Core interval remains valid | Core seal check may still pass for frozen request data; Aitia's fresh use check must reject the stale dependency and invalidate affected local receipts through their actual Core owner where observed |
| Old bytes return after a known invalidating change | Do not revive a revoked/known-stale receipt or erase the observed transition. A supported unchanged-basis recheck may issue a new receipt; reinstated roles/policy require actual qualified source/adoption evidence |
| Only one purpose issues before another fails/times out | Preserve that actual receipt and failed attempt; aggregate stays incomplete. No fabricated rollback or bundled all-purpose receipt |
| New history/counter or denial/withdrawal arrives | Reassess current eligibility at actual source cut; new Q/R if its required input meaning changes. Preserve immutable original C/Q/R and prior receipts/findings |
| Cross-process/host or restored serialized artifacts | Re-establish actual trusted source/custody/current verification through a qualified route. JSON/signed bytes/private IDs do not reconstruct another process's issuance/admission table |

Aitia's qualified public review operation obtains current time from its selected
trusted host/clock policy, with declared units/domain and bounded lease. It must
not accept arbitrary caller now/until values, a backdated instant or an unlimited
lease to pass verification. Core itself only validates the supplied nonnegative
integers/interval; it does not provide a trusted clock or detect every rewind.
Use the shared existing-Host mechanism specified above rather than copy a clock
or lease manager into Scenario. The actual owner extension must retain and
qualify its monotonic/source-currentness guards, clock units and restart domain;
it cannot turn a restarted local counter into portable wall-clock authority.
Fixture calls such as now=10 are logical test premises, not live clock proof.

Core admission indexes receipts at the instant supplied when admission is built.
