* DESIGN WP03 objective and scope
:PROPERTIES:
:CUSTOM_ID: profile-selection-scenario-capture
:STATUS: File/field/call-boundary design; no implementation, capture or execution
:END:

WP03 consumes the checked Library Scopes designed in 10.42/10.43, resolves an
independent Profile request against actual published choices, and captures one
project occurrence input basis C. Scenario owns binding/capture composition;
Library owns reusable meaning/allowed capabilities and expected Contracts;
project owners supply actual project inputs and governance. Core continues to
own source admission and linking. C is a POO value with actual source/acquisition
associations, not another configuration language, global context manager or
serializable permission token.

There is one authoritative captured basis for each occurrence. That does not
mean one global C for all projects, one capture forever, or that output evidence
is inserted into C. New selection/required inputs produce a new basis; retries
and derived observations keep their separate A/E/W associations from 10.39.
Q and R refer to that same C, actual results and qualified uses. No call may
reconstruct a different source/Profile/tool/policy selection beside it.

The shared declaration Contract remains the sole V1 generation owner. A Profile
can constrain provider/subject choices but cannot author that generation, select
an arbitrary validator or resolve a latest version. The current responsibility-
based filenames and the API naming decisions in 10.42 remain in force.

* SPECIFIED Profile request fields and supported choices
:PROPERTIES:
:CUSTOM_ID: profile-request-fields
:END:

The target public Profile has the following effective fields. Common request
shape and concrete role-specific parameter admission compose through POO Types;
resolve the expected parameter Contract from the actual published role before
validating its child. Do not validate the full Profile as today's flat parameter
record or accept arbitrary parameters under a generic Any placeholder.

| Profile field | Meaning / checked boundary |
|---------------+---------------------------|
| identity | Stable name of this reusable selection request; no new version/revision counter and no assertion of actual source or authority |
| selection | model-role is one of the Scenario's actually advertised generic-model/rust-model/integration roles; review-policy is a published stable choice or explicit no-review request; purpose states the investigation/review intent. Optional provider/source constraints only restrict admitted choices |
| parameters | Single reusable parameter child under the selected BackpressureProfileContract, ResourceProfileContract, ResourceSixCaseProfileContract or ResourceIntegrationProfileContract. Its own identity names the parameter choice; semantic parameter fields live here once |
| investigations | Requested supported questions/methods, mode, claim subjects, finite domains and resource limits within Library and trusted host/project policy. Desired method support is not observed execution support |
| products | Requested product roles/viewpoints and explicit optional additions under the adopted stage requirements; cannot replace the required product/duty inventory |
| project-constraints | Explicit expected subject/revision/baseline/prior-review constraints when requested; these are comparison constraints, not a second authoritative project occurrence. Absence is explicit in the effective Type, not an implicit latest/current-directory choice |

Existing LifecycleProfile.identity and LargerPayloadProfile.identity may retain
their resource-64/resource-128 names. Move their numeric/workload/runtime/inventory
premises into distinct typed parameter values in that same Profile file. Give
those values meaningful parameter identities rather than maintaining a second
copy of each number/string on the outer Profile. LargerPayloadProfile selects
its larger parameter child through POO specialization; IntegrationProfile selects
the same qualified parameter choice plus the integration role/request. Direct
assignment selects a value; inherited refinement is reserved for extending an
existing value. These are target definitions, not added APIs in this turn.

The Lifecycle default is a bounded Rust mechanism investigation request. Any
no-review purpose still needs actual trusted project permission; the default
does not exempt review requirements. Gateway fixture choices remain formal/
fixture investigations until actual project inputs qualify the requested use.
Parameter values valid for a model do not necessarily satisfy the controlled
six-case method or its QNT initializer. Capability checks retain those distinctions.

Required factors derive from the selected model/ancestors, premises, policy and
actual project requirements; requested factors add supported concerns and cannot
delete mandatory ones. Caller-selected budgets cannot enlarge host limits or
convert timeout into expected success. No policy, validator, version resolver,
method implementation, role grant or signing key is supplied through a Profile.

* SPECIFIED Consume checked Scopes and bind one selection
:PROPERTIES:
:CUSTOM_ID: scenario-checked-scope-binding
:END:

The target ResourceLifecycle Scope advertises all three model roles. Its existing
interface gains an explicit Generic requirement for backpressure-memory under
BackpressureScopeContract, alongside Domain/rust-resources and Evidence. init.ss
already names these providers; no new dynamic loader follows a Profile string.
A Scenario advertising only Rust/integration needs only the corresponding
published provider route, but may not claim Generic callable/parameter support
merely by traversing Rust.entry.parent.

Explicit requires are resolved at Scenario demand, before this Profile model
choice. A Scope advertising all three roles therefore still requires its declared
Domain dependency when Generic is chosen. It does not promise Profile-dependent
pruning or lazy loading of an invalid required provider. An independently usable
Generic-only application must assemble an explicit Generic-only provider/Scenario
route using the same Contracts/operations; parent-only Core selection isolation
is a separate check, not an implied property of this all-role Scenario.

| Requested model-role | Actual checked value / expected Contract | Parameter/capability and ancestry binding |
|----------------------+------------------------------------------+------------------------------------------|
| generic-model | Generic.entry / Generic.entry-contract | Actual generic parameter/method Contracts; parent=false. Bounded Rust review policy is inapplicable |
| rust-model | Domain.entry / Domain.entry-contract | Actual Rust parameter Contracts and requested capability premises; entry.parent must agree with the Generic entry actually associated with this provider graph |
| integration | Domain.integration-entry / Domain.integration-contract | Actual integration parameter/capability Contracts; integration.parent is Domain.entry and its parent is the admitted Generic. Consume mapping/deltas/case-links already published |

These are fixed code-owned associations of explicit requires and export slots,
not a runtime registry controlled by Profile fields. Reject ambiguous providers,
consumer overrides that break the actual ancestor association, skipped/cyclic
parents and forged descriptors before invoking candidate validator methods.
Use returned checked Scope/parameter/selection values. A copied V1/identity label,
plain POO shape or pre-normalization Scope is insufficient.

Binding returns a checked selection value with these logical associations:

| Bound field group | Authority / invariant |
|-------------------+-----------------------|
| provider | Actual required-edge checked Scope and retained Core provider/source/admission/currentness association. A Profile cannot supply a replacement Scope or guard |
| model | Selected leaf and expected role Contract; full ordered actual parent chain and their meaning revisions; source association of every required ancestor |
| declaration | Actual shared declaration owner/read association, consistent across the roles. Generation is read from that owner; no second version setting |
| policy | Published policy and expected Contract, purpose/applicability and actual family association, or explicit absence constrained by the project mandate. Bounded coding policy does not cover all DE-CASE-01 design duties |
| profile | Returned effective Profile and its parameter/capability checks, with required domain/mode/limit constraints and source/read dependencies |
| requirements | Library/inherited duties, integration roles when selected, policy/stage/product requirements and relevant trusted project mandate references. Expected inventory is derived independently of supplied files/results |
| project-request | Explicit project/purpose/occurrence constraints and qualified source/mandate-provider association needed for capture; not an already observed project implementation or an approved adoption |

Project policy/mandate and role records are actual inputs with origin and trust
limits. Bind checks what the trusted project source can establish and records
missing/unverified governance as gaps; it cannot authenticate a grant solely
because the request includes a name. Actual context/content/authority verification
still occurs through WP07/WP08. Unknown mandatory policy/adoption requirements
prevent a ready review, even if a descriptive selection/capture can be retained.

Recheck expected source/descriptor/read associations before capture. A changed
binding creates a new selection; it cannot rewrite a retained C. Model and policy
references may be live POO values at binding time, so capture must own their
relevant effective meaning/read basis rather than merely retain pointers whose
contents can later change unnoticed.

The complete selected-policy route includes WP05's design policy explicitly:

| Requested supported policy | Trusted export / expected descriptor and limit |
|----------------------------+------------------------------------------------|
| Bounded coding-method policy | Domain.review-policy / Domain.review-policy-contract; only its declared coding purpose/scope |
| DE-CASE-01 design-review policy | Domain.design-review-policy / Domain.design-review-policy-contract; distinct fixed policy identity, authored semantic revision and required content/history/delivery constraints |
| Explicit no-review request | Only where actual project mandate permits the stated operation; cannot remove an independently mandatory review duty |

The trusted selector maps a supported identity/purpose to these fixed export
associations, then checks actual applicability/role/source/family/currentness.
No candidate selects its validator. Unsupported policy/model combinations refuse;
Generic selection cannot acquire this Rust case policy merely from its presence
in an all-role Scenario. Content operations use checked methods/method-contracts;
requests cannot add Config options, new providers or another mandatory inventory.
SC policy/capability/source controls include both policy choices.

* SPECIFIED Separate Library, project, subject and tool inputs
:PROPERTIES:
:CUSTOM_ID: capture-input-ownership
:END:

| Input owner / role | Included basis and resolution | Limit |
|--------------------+-------------------------------+-------|
| Library provider | Selected definitions/Types/policy/mapping/deltas; relevant reader/observer/generator/method/framework source and actual compiled/loaded association; published formal assets and dependency context | Resolve against admitted provider/source ownership, not target project cwd. Declaration generation and semantic revision do not identify all loaded implementation bytes |
| Reference workload | Provider-owned controlled Rust crate/lock/source and its declared test protocol when that is the actual method subject | Bind a reference-workload subject. Its six-case pass/counter evidence is not a result about an arbitrary network-service implementation |
| Target project | Actual repo/worktree/source-root and source/lock/build/model/config/dependency inputs, including relevant dirty/untracked/external inputs, project subject/revision/scope and declared implementation subject | An arbitrary crate cannot satisfy the reference six-case protocol merely by being passed as crate. Missing project instrumentation/correspondence is an unsupported method/claim gap |
| Tool/runtime/acquisition providers | Actual executable and relevant backend/library/environment/config inputs, trusted input readers and their implementation/source association | Exact bytes/version output alone do not close transitive reads. Explicitly bound inspection providers may discover dependencies under bounded Core Ops; capture does not secretly run verification methods or build a project to manufacture evidence |
| Architecture/document/decision products | Actual selected model, actual/target labels, D01-D10 section/anchor/byte/reference closure, DE-R/DE-O/decision links and assumptions | Resolve relative references against their owning artifact/source context; authored prose and a successful link check do not establish substantive adequacy |
| Project governance/history/recipient | Actual policy adoption/mandate/role sources or gaps; required prior-review/failure/counter records, authoritative source inventory, intended recipient/access constraints when required | Captures record the real input cut and limitations. Later fresh history/authority discovery remains required; captured names do not issue decisions |

Provider and project roots may coincide in this repository while retaining their
separate logical roles. In an external repo they usually differ. Runtime paths
are explicit resolved associations; documentation may present relative references.
A selected source is never silently changed by later cwd, environment heuristics,
a shared project ID or a different worktree with the same HEAD/revision string.
Relevant symlink/external resolution must be supported and captured by the actual
source provider, not guessed from a normalized path label.

Current Cargo ancestor/CARGO_HOME configuration and RUSTFLAGS/wrapper/toolchain
checks remain relevant. They must follow the real project/workload and execution
context rather than only the Library checkout. Acquisition or later execution
that discovers an unbound relevant input stops that use: qualify a new capture
or use a previously qualified immutable-source domain that already contains it.
Do not append previously unknown ambient inputs into an existing C after a run.

* SPECIFIED Captured value C, acquisition and lifetime
:PROPERTIES:
:CUSTOM_ID: captured-use-fields-and-acquisition
:END:

| C field group | Required content / invariant |
|---------------+------------------------------|
| identity / input-basis | Actual occurrence association and complete owned meaning/input basis under the qualified producer/encoder/source boundary. A digest or public ID alone is not proof of acquisition or permission |
| selection | Captured effective selected model/role/family/ancestor/policy/Profile association from binding; semantic revisions and relevant read/source observations. Profile parameters have one authoritative location here |
| project | One actual project subject/revision/scope/root/worktree/purpose/stage/occurrence value, checked against project-request constraints and actual selected inputs |
| provider-inputs / project-inputs / tool-inputs | Typed retained input observations with logical role, actual origin/owner, owned bytes or qualified immutable reference, content/source identity and acquisition/currentness limits. Shared artifacts may be referenced under several roles without independently authoring their bytes |
| subjects | Explicit observed target/reference-workload/model subject associations and correspondence obligations. Provider reference evidence cannot be relabeled project evidence |
| requirements / inventory | Required duties and input/product/method roles derived from the actual selection/mandate versus actual acquired bindings. Missing/duplicate/conflicting/inaccessible/unsupported roles stay explicit |
| products | Architecture, Org/decision/section/reference associations pointing to the actual acquired input values; no second copy of product bytes or invented semantic findings |
| mandate / prior references | Actual selected policy/adoption/role/initial-baseline/prior-review/history-source inputs and unresolved claims; preserve original subject/revision/scope and historical status |
| acquisition / provenance | Actual trusted acquisition/read operations, source/compiled/loaded provider association, owned-reference access and relevant guards. No caller-supplied current! callback is accepted as its own authority |
| gaps / use constraints | Typed gaps and operation-specific acquisition/input/domain limits. No universal captured?, complete?, executable? or approved? field promotes the value into evidence/review authority |

C's public fields are inspectable POO values. Their acquired input associations
are checked through the actual Scenario/host acquisition owner and existing Core
source/admission mechanisms at use, not a callback or checked flag selected from
untrusted public fields. Owning those associations may require private retained
input state within the existing operation owner; that is not a second global
capture registry. A presentation copy/serialized record cannot reconstruct a
private source capability or live receipt. Actual compatible source re-admission
and input acquisition are required across process/host boundaries.

Acquisition proceeds in this order:

1. Recheck the bound checked Scopes/descriptors, effective Profile and project
   constraints; derive required duties, input/product roles and qualified readers.
2. Resolve each input under its actual owner and acquire owned bytes or an
   actually qualified immutable-source reference, retaining origin/read limits.
   Normalize supported lazy values under their declared dependency guards;
   arbitrary hidden external callbacks remain open inputs, not presumed pure.
3. Check actual bindings against independently derived expected inventory and
   relevant transitive closure. Record gaps; never infer completeness from the
   supplied path list, omit relevant dirty files or hash every unrelated repo file.
4. Validate/admit the full effective Context and contextual associations; retain
   and return its checked value with the actual acquisition basis. If normalization
   changes a referenced value, all effective associations must remain coherent.
5. At each later operation, its trusted required Contract checks relevant owned
   inputs, origin/currentness and claim constraints. A caller requesting a weaker
   purpose cannot bypass the stronger Contract of the actual operation invoked.

Reference closure follows declared typed roles under bounded traversal. Repeated
shared references retain their role association; incompatible duplicate identities
refuse the affected closure. Architecture/reference graphs may contain cycles;
that does not permit engineering parent cycles or an unbounded recursive read.
Supported readers retain visited identities and declared input/size/work limits;
unresolved or limit-exceeded closure is an explicit gap. Parsing/semantic criteria
not yet supported by the relevant observer remain open, not guessed by a path list.

Occurrence identity, input-content identity and execution identity are distinct.
Two captures with identical bytes need not be the same occurrence; a repeated
usage label is not provenance. Consumers bind the actual owner/source-associated
C, and cross-C evidence reuse still needs the fresh qualified use association
from 10.39. Bounded method request variations are allowed only within the captured
request/capability domain; changing the effective Profile/required basis needs a
new capture rather than an unchecked per-call override.

The guarantee is one owned byte/meaning basis with declared guarded origin/use
conditions. It is not an atomic whole-filesystem snapshot. Before/after hashes
cannot exclude every change-and-restore race. A method/policy requiring a stronger
snapshot needs a qualified provider for it; otherwise that use remains unsupported.
Core source/object read guards retain their actual scope and do not imply a new
whole-project snapshot service.

Methods must consume the owned inputs/qualified immutable provider. Merely checking
a path and then reopening mutable ambient bytes does not satisfy this guarantee.
A retained historical basis can remain inspectable while current applicability
fails after source/grant/history changes. Missing reviewers/products may permit
an honest draft C or unrelated qualified analysis, while blocking the particular
method or ready review requiring those roles. Structural acceptance is separate
from all such operation admissions.

Generated QNT/SysML files, Rust observations, A/E/W/use results, Q, R, verification
receipts, decisions and generated views are later outputs; they do not mutate C
or hash themselves into its inputs. Derived A may bind an actual upstream W as
specified in 10.39. Output storage is supplied to its actual operation and recorded
with E; if destination/configuration can affect execution, the relevant premise
must already be qualified/bound or the operation refuses that unbound input.
No output path silently adds ambient Cargo config/environment to the basis.

Changing model/policy/parameters/project/required input meaning or relevant source
closure creates a new binding/capture as appropriate. New attempts and newly
arriving evidence under the same C remain separate outputs. Later decision/history
updates trigger fresh applicability/discovery/R, and a new Q if that history was
query input; actual changed captured mandate/requirements need a new C. The old
C is never silently refreshed or relabeled current.

Captured governance record bytes and later current-status observations have
distinct lifetimes. Changed captured appointment/grant/policy/project content
requires new C when it alters that captured basis. A later status/withdrawal event
about an unchanged captured record is checked at current use/history and need not
rewrite C; it can still block use immediately at that qualified owner boundary.
If that status changes technical demands/products or selected inputs, recapture
or obtain new Q/R at the affected boundary. No perpetual cached grant verdict is
stored in C. See [[file:10.52-contract-consistency-and-implementation-order.org::#consistency-change-impact][the consolidated impact rules]].

* SPECIFIED Operation Contracts, adapters and direct migration
:PROPERTIES:
:CUSTOM_ID: selection-capture-call-boundaries
:END:

Names below specify the proposed public Scenario responsibilities, not code added
in this task. Each operation is a POO Function Type using the actual expected
selection/Context/result Contracts. Library parameter/Context Types expose domain
shape/constraints; Scenario Types add occurrence/provider/project associations
without copying those field maps. Generic capture uses its appropriate effective
Context Type; it does not fabricate Rust premises or require a Generic library
context-contract export absent from 10.43.

| Boundary | Proposed input -> output | Required owner checks |
|----------+--------------------------+-----------------------|
| Scope assembly | Core checked Generic/Domain/Evidence and qualified host dependencies -> Scenario Scope | Correct required-edge/final-Scope candidates; matching ancestors/family; actual trusted acquisition operations and callable Contracts |
| bind | Profile + explicit project-request/mandate-source constraints -> checked bound selection | Scope/role/policy resolution, returned normalized parameters, supported domain/purpose, required inventory and gaps. No caller-provided validator/provider replacement |
| capture | That bound selection + actual project/input-source bindings -> checked C | Inputs must match the bound source/project constraints; actual acquisition/currentness/closure and contextual admission. No replacement Profile/root/role beside selection |
| current! | C plus requested diagnostic/use purpose -> checked current-use assessment or refusal | Trusted owner derives applicable checks; no recapture/mutation. An assessment at an exploratory purpose cannot authorize a stronger operation |
| observe / method entry | C plus bounded application request and actual output destination -> later A/E/W | Method's own required input/claim/issuer checks under WP04; no free-standing root/Profile/crate/tools beside C |
| open-evidence | C plus actual qualified applicable results/uses, including empty initial evidence -> Session/identified Q under WP06 | Derive catalog/required duties/program sources from the same association; explicit pending duties survive before results arrive. No arbitrary snapshot/scope row override |
| prepare-review | C plus exact Q/uses and actual additional review inputs -> R/dossier draft | Same project/policy/product/authority basis; additional inputs cannot override captured selection or hide counter/gaps. Real verification/disposition remains WP07/WP08 |

The Scenario Scope publishes bind/capture/current! and the actual qualified
operation surfaces at their declared stage. The current open-review name is
replaced by open-evidence for inference; Aitia preparation is explicit. No public
entry alias fixes every request to base Rust. Any methods view is bound to the
selected/captured association and enforces the same C/source boundary; forwarding
a raw Library method with a bypass set of arguments is not the target API.

Direct migration covers both Lifecycle and Gateway. Remove the public raw
snapshot/source/captured-scopes route; retain finite Gateway row construction as
an explicitly bounded fixture/test utility under its original meaning. Integration
drivers select published integration-entry through bind rather than construct
