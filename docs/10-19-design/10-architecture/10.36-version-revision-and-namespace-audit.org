* AUDITED Scope and decision boundary
:PROPERTIES:
:CUSTOM_ID: native-version-usage-audit
:RECORDED_ON: 2026-10-20
:STATUS: Read-only source audit and adjustment design; no implementation or review submission
:END:

This audit compares the existing backpressure Library, gateway/resource Profiles,
Scenarios, method observations and local Aitia consumer against 10.26. The source
baseline is HEAD =8044732d505f84e373119a70f947df00e1767300= plus the active dirty
checkout. HEAD alone does not identify these inputs. Source links below locate
the inspected definitions; they are not immutable evidence references.

The public contract generation requested for this work remains V1. The proposed
native Library slot is absent, so there is no qualified native version read.
This document does not declare its value, introduce a registry or change package
versions. Findings concern ownership and use, not a blanket renaming of strings
containing digits. No runtime, QNT, Lean, ASCENT or Aitia check is executed here.

Inspected surfaces are native declarations/Contracts, selection and exports,
Scenario capture, digest construction, observation/registration, review packets,
reassessment and archive readers/writers. Relevant test sources are inspected as
future regression controls, not reported as passing. Upstream internals are
sampled only where needed to establish the existing POO/Core ownership boundary.

* AUDITED Distinct meanings and rightful owners
:PROPERTIES:
:CUSTOM_ID: version-meaning-and-owners
:END:

| Meaning | Native owner / reader | Required interpretation |
|---------+-----------------------+-------------------------|
| Public Library contract generation | Owning Library declaration; consumer reads the selected admitted export | Proposed contract-version metadata; not yet present; Profile cannot override it |
| Model/specialization semantic revision | Library definition of that model, extension or mapping | Identifies engineering meaning; no ordering or compatibility is inferred from its suffix |
| Selected project revision | Project occurrence selected by a Profile and bound by Scenario/review | Revision of the reviewed subject; independent of the reusable Library contract generation |
| Wire schema or digest-domain tag | Producer/reader or algorithm that owns the representation | Selects decoding/validation or hash interpretation; not a package namespace or Library release |
| POO object-revision / Core source generation | Native POO/Core state and admission mechanisms | Invalidation/currentness identity; not a user-maintained revision counter |
| Package, dependency and executable version | Native package manifest, Cargo metadata/lock and tool observations | Identifies dependency/tool inputs; a displayed version is insufficient without its applicable source/binary/configuration closure |
| Content digest and receipt identity | Captured bytes and issuing evidence/review owner | Equality binds the actual content/occurrence; matching contract labels do not authorize receipt reuse |
| Namespace / Module / semantic identity | Existing package/import declarations and native identity fields | Stable routing and subject identity; place contract generation in native metadata, not in new paths or suffixed identities |

A selected project revision is a legitimate independent Profile parameter. It
must not be replaced by the Library contract generation. Conversely a Profile's
identity must not act as the authority for reusable policy meaning. Public policy
identity, project revision, Profile identity and evidence encoding are separate
responsibilities even when today's fixture places them in one object.

The framework boundary is already explicit: [[file:../../../.gerbil/pkg/github.com/tao3k/gerbil-poo/object.ss][POO object-revision]] tracks native
state; [[file:../../../.gerbil/pkg/github.com/tao3k/poo-flow-core/module-system/source/publication.ss][Core publication validation/currentness]] checks its own native descriptors;
[[file:../../../.gerbil/pkg/github.com/tao3k/poo-flow-core/module-system/authoring/admission.ss][Core authoring admission]] keeps stable diagnostic kinds separate from source
revisions. Keep these mechanisms. Domain contract metadata is a Library concern,
not a reason to extend Core with another release registry.

The actual Namespace finding is VA-03: no contract-version suffix is present in
the inspected public package/Module paths. VA-10 is a version-bearing semantic
policy identity, not a Gerbil namespace. Both distinctions matter: no package
renaming is needed, but new public policy publication must separate identity and
metadata. Historical producer/adapter identifiers and wire records retain their
original bytes; do not rewrite them to simulate the target design.

In particular, the existing policy token in an evidence packet may remain an
explicit producer-owned encoding identifier. Its native policy declaration must
reference that encoding deliberately; a wire token does not become the stable
public policy identity or a second contract-generation source. Do not silently
rename a signed/hash-bound token, reinterpret its decoder or create an identity
alias registry. Any changed packet representation needs its own qualified
producer/reader contract before use.

* PLANNED One native association through the existing evidence chain
:PROPERTIES:
:CUSTOM_ID: version-evidence-association
:END:

The proposed flow is the existing 10.26 path: native Library declaration ->
Config/core.exports -> admitted required scope -> Scenario capture -> issued
method results and ASCENT projection -> local Aitia request -> Org/D2 explanation.

The capture must associate the owning Library declaration/source identity,
selected entry identity and semantic revision, observed contract metadata,
validated Profile selection, project subject/revision/scope where applicable,
and actual method/content closure. These are logical responsibilities, not a
new Scheme record, registry or serialized schema. Reuse the native objects,
existing Context Contracts and producer-owned evidence references.

There are two current paths: ResourceLifecycle checks its Context and selected
entry; the integration projection is opt-in; GatewayReview still permits a
caller-supplied snapshot/source/scopes for its fixture route. They must not be
described as one already completed capture. Retain the fixture route's bounds;
qualify the real native association for the selected production-facing route.

The current project ASCENT program compares required input keys/digests and
checked witnesses. It does not contain a Library contract-version relation.
Validate the association before projecting selected catalog rows; do not add a
second version resolver or assume Core publication admission already checks the
missing domain metadata. Only add an obligation input when its declared semantic
footprint needs it: appending a version key to every witness would conflict with
existing extra-input rejection and unnecessarily invalidate unrelated results.

Reuse remains governed by applicability and actual input identity. The same
contract generation cannot justify reusing a receipt for changed bytes. A changed
project revision does not erase a counter; any permitted content reuse still
requires fresh revision-bound review verification. Different owners or contracts
cannot be treated as equivalent by comparing their version strings. No implicit
compatibility range or lexical ordering of revision labels is introduced.

The local Aitia adapter consumes the exact selected occurrence and policy
association. Native Aitia project/rebase/disposition authority remains external
to this Library; a local class-a fixture is not institutional classification or
approval. Protocol decoding and cryptographic/history checks remain with their
existing producers/readers. Moving reusable policy meaning does not move those
trust boundaries into a Profile or an ASCENT fact.

* PLANNED Refactoring dependency order and acceptance gates
:PROPERTIES:
:CUSTOM_ID: version-adjustment-order
:END:

The steps refine DE-T01/T02/T03/T05 in 10.33 and the C5 slice in 10.35. They are
future implementation gates, not completed refactors or version increments.
The user has removed the smallest-diff constraint. [[file:10.37-library-declarations-and-contract-design.org::#declaration-contract-architecture][10.37 now specifies the full
native Contract architecture]], replacing the flat model version-slot proposal
with a shared Library declaration Contract and distinct role Contracts. Engineering
parent relations and composed review policy remain separate. The order below is
a dependency sequence, not a restriction on refactoring scope.
[[file:10.38-profile-selection-scenario-capture-and-evidence-use.org][10.38 expands Select/Capture and evidence/review use]] into the full target
architecture: request versus bound selection, one captured basis, method-specific
applicability and identified query/review outputs. No new implementation is implied.
[[file:10.39-method-execution-evidence-issuance-and-ascent-projection.org][10.39 expands methods, issuance and projection]], including the distinction between
declared footprints and the broader actual implementation/validation closure, and
application-scoped expected inputs. These refinements require future refactoring,
not a change to the native generation or historical schema labels.

| Order / owner | Target responsibility and finding coverage | Acceptance required before advancing |
|---------------+----------------------------------------+--------------------------------------|
| Declare / Library | VA-01/02/04/08/10: native shared declaration Contract owns generation; separate role Contracts reference it; abstract/Rust objects own semantic definitions, mapping/delta and composed review policy; refactor existing scope Contracts as specified in 10.37 | One native source for each public contract/policy declaration; valid selected entry exposes it through current exports. Missing/malformed metadata, unauthorized inherited override or a foreign owner association is rejected. Rust/integration semantic revisions retain their own meaning; no directory/namespace migration |
| Select / Profile and Scenario | VA-05/06/10/11: keep independent Profile values; select published policy and Library; make the initial project baseline an explicit trusted occurrence selection | Profile cannot mint Library metadata or satisfy policy selection by copying an identity string. A selected project revision is validated as a project revision, not forced equal to contract generation. Wrong initial pin or missing required prior review blocks use; fixtures stay visibly fixtures |
| Capture / Scenario and native methods | VA-07/08/09: add the admitted native association to the same actual input capture and currentness checks; generator/scope read the same mapping definition | Swapping Library owner/entry, changing contract metadata, semantic definition, Profile, mapping or relevant bytes invalidates the affected binding. Replacing an entry by another with equal-looking labels cannot authenticate it. All supported capture routes enforce this association; old snapshots are historical |
| Project and verify / evidence adapters | VA-09/11/12: consume the same association in result admission, selected catalog projection and exact Aitia request/policy binding | Reject raw/forged/foreign bindings before admitted support; preserve missing/extra/mismatch rules. A changed project revision needs the appropriate fresh receipt and retains unresolved counters. Same version does not admit changed bytes; historical schemas retain their original validated interpretation |
| Display and qualify / Org, D2 and maintainers | VA-03/12/13/14: project observed native metadata/provenance and keep historical references; run focused controls after implementation | Editing a view or Org property cannot alter the native value or create support. Missing native metadata stays unavailable. Namespaces/imports stay stable. Existing source-bound tests and the new association controls pass on the actual changed baseline before any broader qualification claim |

The first two steps establish owners and trusted selection; the third establishes
what was actually used; the fourth checks that association at use; the last
renders and qualifies it. Refactoring must follow the semantic boundaries in 10.37. No manager,
compatibility facade or automatic version increment is needed. Consolidate only duplicated
meaning owned by the same native declaration; do not centralize every private
wire tag, executable version or project revision into a global constant.

** Focused future controls

| Control | Required distinction / expected refusal |
|---------+------------------------------------------|
| Missing or overridden native version | An absent slot, malformed value or unauthorized specialization override cannot create a qualified binding; Org defaults cannot repair it |
| Same label, foreign owner | Equal contract/revision labels from another Library or entry are not the selected admitted declaration |
| Meaning changed, labels unchanged | Changed rules, mapping or source bytes require affected checks/recapture; unchanged labels do not preserve currentness |
| Project revision changed | Preserve carried counters and prior-review requirements; an old receipt cannot answer a fresh revision-bound request |
| Initial baseline mismatch | An arbitrary Profile revision cannot bypass the explicit trusted initial selection after removing a consumer literal |
| Policy or Profile impersonation | Copying a policy identity/contract label into a Profile or packet cannot replace the selected native association |
| Footprint controls | Wrong, missing or extra declared inputs still yield mismatch/non-applicability; no unrelated global version input is injected |
| Historical schema and packet replay | Preserve each reader's sealed/prefix/head/signature checks; replacing a schema token or relabeling an old packet does not upgrade evidence or authority |
| View-only alteration | Changing an Org property/D2 label cannot change the native value, admit a witness or issue a review receipt |
