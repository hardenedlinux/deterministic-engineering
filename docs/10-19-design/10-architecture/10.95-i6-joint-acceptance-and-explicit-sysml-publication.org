* Scope, activity selection and separate verdicts
:PROPERTIES:
:CUSTOM_ID: i6-scope
:END:

I6 unifies the joint acceptance specification for the complete declarative slice
with its separately requested SysML publication effect. It refines A5 using I0--I5;
10.88's I7 remains the later execution of joint acceptance and the separate study.
This does not renumber I7, implement a coordinator or authorize that execution.

#+begin_example
Declared Project -> qualified sources -> Core K1 / consumer SD / final S1
 -> admitted Library/Module -> checked Profile/Scenario -> original capture C
 -> actual Program + complete projection -> recognized accepted frozen view
 -> selected candidate/plan/catalog/mapping -> exact candidate bundle O
 -> independent conformance/language/property outcomes + actual current use
 -> separate explicit Project request -> guarded expected B -> O transition
 -> observed effect/product closure -> separate mechanism / case / research verdicts
#+end_example

This is Org/D2 design only. No implementation, package or model edit; build, loading,
cold start, restoration, acquisition, inference, validation, acceptance, publication
or orchestration execution occurs. Document lint/export/link checks and D2 rendering
are document checks only. Every control below is proposed, not a completed receipt.

| Verdict | Required conclusion |
|---------+---------------------|
| Mechanism and lane correctness | Exact positive/negative controls exhibit independently expected semantics, actual selected sources/loads, complete nonzero case inventory and bounded termination. Correct refusal is a valid control outcome |
| Actual DE-CASE-01 completion | Every mandatory stage, cross-stage association, advertised lane and document/product obligation of the preselected activity closes. A correct refusal, probe or candidate-only outcome cannot establish this positive verdict |
| Research comparison | A separately predeclared matched protocol supports, refutes or leaves uncertain a hypothesis. Better LLM proposals, causal explanations, reuse or cost are not required correctness outcomes |

Select the activity before execution: candidate-only, explicitly permitted root-only
publication, or an actually supported broader product activity. These are activity
scope descriptions, not new purpose/action enum literals. The effective Library
policy/Contracts supply the existing finite domains. Do not invent an Aitia purpose,
a new policy grant or a compatibility version for model publication.

Library publishes reusable obligations/policies/catalog/mapping/method expectations;
Profile selects supported scope, products, policies and methods; Scenario binds actual
project inputs and original C; Module owns reasoning, materialization and validation
bindings; Project owns the separately permitted effect and validation entry. Org/D2
explain those associations. Library has no hardcoded host target and ASCENT has no
filesystem publication or authorization role.

A partial design activity may retain explicit assurance gaps only under its already
selected policy. Missing mandatory model inputs, origin or publication conditions
remain blockers. LIB-C01's historical structural coverage with capability gaps is
not evidence that the complete positive case can publish. Never narrow the advertised
activity after failure to relabel it complete.

* Explicit publication request and guarded state transition
:PROPERTIES:
:CUSTOM_ID: i6-publication
:END:

| Request/observation field group | Required association / owner |
|--------------------------------+-------------------------------|
| Selected activity and intent | Explicit actual user/project publication intent and policy-permitted scope; responsible role/mandate if required by the selected policy. Profile selection alone is not authorization |
| Original chain | Recognized C/origin/basis, accepted view/Program/source cut, exact candidate/plan/catalog/mapping/method and required validation/current-use refs |
| Exact proposed effect | Owned immutable candidate O and complete support closure, exact target/worktree/path/object identity and permitted write set; actual/target classification and projection limits retained |
| Expected prior state | Captured root B plus necessary parent/support/source state, or explicitly captured qualified absence if creation is supported; no force/overwrite default |
| Effect guarantees | Actual selected exclusion/check-and-replace primitive, protected target/support domain, interval semantics, crash/durability promise, finite limits and cancellation behavior |
| Attempt and outcome | Actual operation/source/producer/request association, prechecks/exclusion/transition/postchecks, observed old/new/current bytes and support, completion/limits/errors. Report fields are observations, not an issuer |

1. Produce and validate O outside the captured input set. No generated artifact,
   report, validation outcome or publication result is appended to the original C.
   The candidate manifest closes exact candidate/support inputs before outcomes;
   no manifest needs to hash itself or its future receipt.
2. Separately prepare the explicit request from actual I5 outcomes and the selected
   permitted activity. A dry inspection of that request has no publication effect.
   Eligibility requires all mandatory binding/content/tool/policy conditions, not
   only structurally_covered, declared_ready, finished, FORMATION-OK or exit zero.
3. Re-establish actual current-origin/use, policy/mandate/premise checks and expected
   B/support. Resolve the actual worktree/target and aliases inside the protected
   domain, including relevant symlink/hardlink/parent-directory replacement cases.
   A supplied path or old realpath is not sufficient identity under concurrent edits.
4. Establish the qualified exclusion and guarded replacement over the required
   domain. A preceding hash comparison plus ordinary write/rename has a race. An
   advisory lock only proves exclusion for covered cooperating writers; it cannot
   establish safety against other writers. Select/qualify a supported mechanism
   or keep that broader activity blocked; do not claim a generic filesystem CAS.
5. The intended transition is exactly B -> O at the selected root with required
   support stable. Use the actual qualified primitive and protect immutable staged
   bytes against substitution. Atomic root replacement, durable persistence and
   multi-file consistency are separate promises, each requiring its own controls.
6. Observe actual O/target/support after the effect and required current-use checks
   over the declared interval. Original C still records B; this intended change is
   not a blanket exemption for other stale inputs. Postchecks must distinguish the
   permitted output from unrelated edits and invalidated supporting premises.
7. Record transition occurrence separately from completed valid publication. If the
   effect occurred but a postcheck, log/result write or live eligibility check fails,
   retain actual state and incomplete/invalid/unknown conclusion; never claim rollback.
   A later expiry affects current reliance without rewriting historical observations.

The validity interval must be supportable by the actual owners. Remote mandate or
premise checks cannot be made atomic with a local file rename merely by sequencing
calls. Use genuinely supported leases/guards with explicit scope and trusted time,
or state the weaker observed interval and leave an activity requiring a stronger
guarantee open. No fixed-instant verifier is converted into a moving clock.

A root-only request cannot claim atomic root/companion/Org/D2/catalog publication.
All selected mandatory document products still require their own content/reference
closure before complete activity success. For a promised multi-file effect, qualify
an actual transaction/visibility protocol or keep that promise unsupported. This
design does not silently add one, authorize Git commit/push, full Aitia review,
Library delivery or receiver adoption.

* Failure, replay and three separate recovery domains
:PROPERTIES:
:CUSTOM_ID: i6-recovery
:END:

| Cut/event | Expected state / permitted next step |
|-----------+--------------------------------------|
| Refusal before effect | No target publication by this attempt; retain candidate/attempt diagnostics and independently observe actual target if concurrency matters. Native Session failure is not a filesystem rollback |
| Crash/cancellation before replacement | Staged/partial outputs may exist. Inspect actual state; absence of a completion record does not prove no effect. No background child is assumed terminated from parent exit |
| Replacement happened, outcome missing | Observe B/O/other and support; O bytes alone cannot authenticate which request/writer performed the effect. Require actual supported operation provenance or retain unknown completion |
| Concurrent target/support edit or lost eligibility | Refuse before effect where detectable; after an effect, record transition and drift/invalid/unknown current eligibility. Do not overwrite the concurrent state to repair a verdict |
| Replayed old request | Old C/baseline/origin/current-use/mandate and exact target must still qualify. Copied request IDs/digests or a repeated result file grant no authority; stale B cannot overwrite newer work |
| Repeated request and O already present | If actual owner can recognize the original completed operation, report its historical outcome plus separate current-use observation. Identical bytes alone mean only observed equality; no synthetic exactly-once success or automatic second write |
| Core build restoration | Real receiver-local issuance/handoff/current source/compiler/artifact admission restores only selected build eligibility and newly checked Scope lineage, not C/view/model authority |
| Process loss with old C/view on disk | Original-C continuation needs actual producer-supported origin and view recovery plus full current checks. JSON/source hashes/build records cannot recreate private issuer state. If unsupported, same-C continuation remains open |
| Fresh-process restart alternative | A declared separate fresh acquisition produces new C and actual Program/view/validation or supported reuse associations. It is a valid distinct route, never a repair/relabel of the failed original-C continuation |
| Publication-state recovery | Actual effect owner recognizes permitted target state and request provenance under its crash/durability contract; recovered build/C alone cannot authenticate past publication. Do not reissue an unknown effect blindly |

Any durable attempt/outcome association needed for crash or replay promises must be
provided and qualified at the actual effect owner. The current report writer is not
such a protocol. No project-local ledger, issuer registry or persisted success bit
is introduced here. A new attempt/retry must preserve prior failures and perform
its actual current checks; retries do not imply exactly-once or crash consistency.
