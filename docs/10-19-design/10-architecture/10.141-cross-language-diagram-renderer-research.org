* Scope correction
D2 is an authoring language and a primary project input. It does not delimit the
research ecosystem or prescribe every downstream visual rendering decision.
Architecture diagramming, graph visualization, constraint-based drawing, routing,
icon systems and AI-assisted diagram design must be studied across languages.
C4/Structurizr remain viewpoint references. No additional modeling DSL or proof
ledger is selected by this research.

The c8b95c0 implementation in10.140 is a functional prototype, not an accepted
visual baseline. Its19 tests establish API/input properties, not layout quality.
Its TS compositor primarily surrounds finished D2 geometry. Adding icons or
shrinking margins cannot give that compositor control of graph-internal layout.
The current samples expose poor spatial balance, small labels after fitting,
overlarge fixed panels and repeated responsibility explanations.

* Correct responsibility split
The intended Library has three independently testable concerns:
1. Question/model projection: use actual OpenSysML and D2 structures plus existing
   project query/evidence associations to select what the reader needs to see.
2. Layout and visual grammar: group boundaries, choose topology, size nodes from
   icons/labels, route edges, place callouts and keep useful whitespace.
3. Rendering/presentation: draw the placed view through reusable SVG/Canvas
   capabilities with downstream themes, icon assets and output profiles.

The existing D2 compiler remains a real source adapter and a comparison
baseline. OpenSysML retains model semantics. ASCENT retains deterministic facts
and inference; Aitia retains review. A view projection can carry their original
IDs and references without creating a new modeling language, evidence database
or self-appointed authority. A private renderer may use a mature engine object;
public Library composition can remain functional and immutable.

No engine is selected by README popularity. G6, existing layout engines and
constraint-oriented alternatives must be compared on actual repository content
and export/runtime constraints before adding a dependency. Pure static output
and interactive inspection are separate requirements and may need distinct
adapters rather than one mandatory browser application.

* Same-case comparison protocol
Use repository90.91,90.120 and90.84 as frozen semantic baselines. Preserve their
original views for regression. Derive question-scoped architecture, workflow and
explanation candidates explicitly; record any omitted/aggregated element and
keep required obligations reachable. Do not improve density by deleting meaning.

For each scope, compare:
- The existing rendering baseline.
- The current TS compositor baseline, retaining its visible shortcomings.
- Candidate visual grammars backed by mature layout/render capabilities.

Keep the same question, model references, required nodes/relations and evidence
status across a comparison. Theme and engine identity are independent recorded
inputs. A compact static figure, an explanatory infographic and an interactive
inspection view must not all be forced into the same tall report frame.

* Acceptance and research questions
| Category | Acceptance / observation |
|----------+--------------------------|
| Semantic correctness | Preserve identity, containment, relation direction and required obligations; disclose aggregation and unsupported notation |
| Mechanical drawing checks | Detect clipped text, unintended overlaps, invalid geometry, invisible required content and routes through unrelated nodes |
| Typography | Compare actual output at its intended viewing size; enlarging the canvas cannot compensate for unreadably small labels |
| Routing | Compare crossings, shared paths, label collisions and unnecessarily long connectors; port semantics must survive |
| Space | Compare occupied bounds, group padding and aspect ratio; use these as diagnostics, not a universal maximum-density rule |
| Visual vocabulary | Icons encode actual kinds; shape, grouping, color and short labels have consistent meaning and an explicit legend where needed |
| Evidence | Missing, conflict and pending remain distinct; visual status cannot establish an accepted Q or review R |
| Reproduction | Record actual engine, theme/assets, source closure and layout options/seed; distinguish reproducibility from aesthetic preference |
| Human comparison | Ask whether each view answers its question faster and more accurately; do not label subjective quality as a formal proof |

LLMs may propose view scope, constraints and alternative candidates, then inspect
rendered results for visual defects. Deterministic validation protects semantics
and mechanical requirements. Human comparison establishes whether an explanation
actually reduces reading burden. ASCENT is not an aesthetic oracle.

* Implementation order
1. Preserve the current prototype, original sources and screenshots as baselines;
   stop treating the fixed report layout as the target framework.
2. Write question/view fixtures with required identities and expected distinctions,
   independent of the source language and the chosen renderer.
3. Qualify focused layout/render candidates for nested groups, icon-rich nodes,
   edge routing, text metrics and static export. Compare complete figures.
4. Select the smallest reusable capabilities that pass those cases; replace the
   prototype composition rather than stacking another wrapper over it.
5. Apply independent themes/icons and connect actual model/evidence references;
   qualify downstream use and publish only reviewed outputs.

Open decisions: renderer/backend selection, exact layout constraint surface,
static versus interactive adapters, reliable font measurement, multilingual text,
asset closure and visual regression policy. No new engine has been installed by
this research and no automatic orchestrator or visual-acceptance claim is issued.

** HTML as a drawing artifact
HTML/CSS and inline SVG are valid primary visual authoring surfaces. A standalone
figure can contain iconography, spatial grouping, annotations, comparison panels
and a compact legend without a navigation shell or long prose document. CSS grid
and SVG each serve the visual problem that suits them. D2 remains available for
model relationships or an embedded subview; it does not prescribe the entire
composition. OpenSysML and existing C/Q/evidence references retain their semantic
ownership across every output surface.

Keep the editable HTML/SVG source. Export the intended figure region to PNG or
other requested outputs through a real browser. [[https://playwright.dev/docs/screenshots][Playwright supports page and element screenshots]];
this establishes an export capability, not our completed exporter acceptance.
Record viewport, device scale, browser identity, theme/assets and source identity;
wait for fonts/images and a deliberately selected animation state. Screenshot the
figure rather than accidentally capturing controls or the full document. Native
browser font rendering is particularly relevant after the observed resvg fallback.
PDF/SVG export should be qualified separately when required.

** Applying the method to this Library
1. Start with the question, audience, actual model/evidence and the explanation's
   intended takeaway. Keep architecture and workflow as distinct visual scopes.
2. Select relevant reference figures and visual metaphors. LLM proposes compact
   layouts, component groupings, icon placement and short annotations; no single
   score or fixed card hierarchy defines the solution space.
3. Render candidate HTML/SVG at the intended reading size and inspect its actual
   image. MLLM critique addresses reading order, ambiguity, whitespace, collisions
   and missing meaning, then the candidate is revised with the user's feedback.
4. Check source/model/evidence fidelity through existing framework owners. These
   semantic checks remain separate from optional aesthetic diagnostics.
5. Retain editable sources, export images and record the selected candidate and
   its associated references. Publication remains an explicit project decision.

This is the revised design direction. The current fixed-width, fixed-section TS
compositor is a baseline to replace, not the contract that future LLM-designed
figures must fit. Public TS APIs can remain functional; themes, icons, source
acquisition and export effects stay independently composable. Existing Agent
capabilities should drive design iteration before adding another orchestration
runtime. No implementation change or live backend/API invocation accompanies
this research update.

Visual inspection of Diagram Design's architecture.png still shows substantial
unused canvas. Its method and output surface are relevant, but this individual
sample is not accepted as our density or iconography baseline. Reference projects
are sources of techniques, not automatic aesthetic winners or fixed score targets.

* Implementation: Deterministic Engineering Render
The package is now @deterministic-engineering/render in packages/render. The
package version remains1.0.0 and is read only from package.json. The old fixed
composePresentation SVG/card compositor is removed; composeFigure accepts a pure

** D2 owns Questions and authored content
D2 already has the [[https://d2lang.com/tour/vars/][vars.d2-config.data plugin metadata mechanism]].
The existing compiler exports it through graph.data. The installed SDK returns
null for nested map values; a JSON block scalar carries the nested figure
declaration correctly. Official D2 parses source/imports; standard JSON.parse
reads that scalar. No second D2 parser or TS Questions registry is introduced.

The90.132/90.133 D2 sources contain Questions, focus/source associations, explanatory
copy, language, purpose, theme layers and model relations. TS contains visual
composition and source reading adapters. A changed D2 question changes the image
without editing TS. relation IDs/directions are retained, and the compositor
refuses requests for undeclared relations. The case is a scoped projection with
explicit model/source links, not a complete SysML semantic validation.

* Visual language, diagram organization and palette are independent
A theme is a visual language: stroke treatment, typography, node/port shapes,
connector appearance, boundary treatment and spacing. Palette layers remain
composable but are not a complete theme on their own. =sketchbook= uses actual
Rough.js strokes and embedded Kalam fonts; =node-editor= adds node ports,
precise borders and a node-canvas treatment. It does not embed React Flow.

Swimlane is an organization of responsibility and order, not a palette.
The D2 figure declaration owns =flow.lanes=, =flow.steps= and =layout=.
Steps bind existing D2 node IDs; their consecutive relations must exist.
A missing lane, node or edge refuses composition. Responsibility labels are
explicit project design declarations, not verified human role mandates.
A business view similarly needs its own business entities/relations and Question;
changing a theme cannot invent these semantics.

Downstream selects ordered theme layers and a layout in the D2 declaration.
Custom layers and functional composers remain replaceable; the package does
not prescribe numbered sections or a universal card layout. Architecture and
Workflow retain independent purposes. Current source/model language stays English.

HTML export measures settled browser text and routes declared connectors against
actual node boxes. Sketch surfaces are marked explicitly with =data-surface=;
font assets and deterministic Rough.js SVG are baked into offline HTML.
Receipts distinguish original composed HTML from materialized HTML, record font
hashes and actual browser identity. These are rendering receipts, not C/Q/R evidence.

browser controls cover deterministic sketch output, changed drawing
parameters, missing connector endpoints, clipping and broken images. The real
case generates architecture and workflow separately, plus sketchbook,
node-editor and workflow-swimlane variants. Actual current source still returns
=capture-blocked / capture = #f=; no accepted inference or published model is claimed.

** Source and evidence invariants
Questions, explanatory copy, current language and source links remain declared
in D2. The model association remains the captured =project.sysml= and D2
projection. Changing a theme/layout changes the rendering footprint, not the model
or evidence status. Every rendered connector is checked against its captured
relation and direction. Matrix axes must reference nodes. Workflow lane
assignments are design declarations, not role-authorization evidence.

Font assets are explicit theme data. Rendering records composed HTML separately
from materialized offline HTML, actual font hashes, drawing/routing package pins,
browser identity and output fingerprints. Rough.js deterministic-seed controls
apply within the qualified browser/font environment; no cross-platform pixel
identity is claimed. The current blocked capture and empty evidence remain visible.
