* I0 scope and non-circular exit
:PROPERTIES:
:CUSTOM_ID: i0-105-scope
:END:

This unifies 10.97's migration design against 10.104's I0 gate and current source.
I0 establishes a reviewed compatible realized dependency/API/prelude/source graph,
actual build/load/test entry capability and an independent complete application
root/lane plan. Framework/bootstrap qualification may precede I1--I6. Final complete
new-application C/view/model/effect/cold/recovery acceptance waits for those stages;
I0 cannot certify their future semantics using a synthetic substitute.

#+begin_example
Native owning declarations -> reviewed actual checkout/dirty/phase cut
 -> real package + entry + prelude registration and qualified POO/Core APIs
 -> explicit required roots -> package-library-spec/native traversal
 -> std/make/Core build issuance -> actual artifact/load association
 -> selected test-source -> TestingScript -> Fixture/Ops/process/receipt/postcheck
 -> I1 and later domain implementation, then final whole-slice lane qualification
#+end_example

This is read-only source/metadata/launcher/selected-artifact inspection plus Org/D2
editing/rendering. No implementation, dependency mutation, checkout move, package
operation, recipe evaluation, tool/version command, build/load/test/acceptance,
cold/restoration, capture/inference/validation/publication or orchestration extension
occurs. Even recipe listing may evaluate shell-backed variables; Justfiles are read
as text. All calls and controls below remain proposed.

Use existing POO value/Function semantics, Core source/build/TestingScript mechanisms,
ASCENT generic execution and Flow product/dev ownership. No parallel graph builder,
compatibility alias, loader, environment-discovery harness or version registry. Library
V1 remains declaration-owned; dependency pins, language identities, semantic revisions
and observed tool/artifact hashes are different dimensions, not Namespace versions.
