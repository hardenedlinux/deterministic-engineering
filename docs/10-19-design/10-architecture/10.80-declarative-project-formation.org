* Input and rule boundaries
:PROPERTIES:
:CUSTOM_ID: formation-facts-rules
:END:

The Scenario reads ordinary POO objects and copies string cells into the existing
ASCENT batch source interface. Those internal relation rows are not a second public
configuration DSL. Candidate identities occur in Profile data and expected test
outcomes, never as branch conditions in the rule program or renderer.

| Relation group | Source | Meaning |
|----------------+--------+---------|
| intent; candidate | Profile project/intent and candidate project/basis | Bind alternatives to the confirmed project goal; changed basis invalidates old proposals |
| proposed_owner/product/duty; capability | Candidate offers | Hypothetical allocations and explicit capability assertions; not attestations |
| required_role; allowed_owner; role_scope; owner_kind; protected_owner | Library roles, owner kinds and protected owners | Independent compatibility and responsibility boundaries |
| required_product/duty/capability | Library demand | Required D01--D10, five DE-O duties and four currently unestablished capability gates |
| project_layout; role_layout; role_dependency | Profile model selection and project layout/dependency declarations | Data-driven package/instance/catalog, model slots, type names, detailed-model references and edges |

| Rule | Actual slice consequence |
|------+--------------------------|
| LR01 | Project-scoped capture assigned to a definition owner yields project-input-in-definition |
| LR02 | Assigning reasoning, review or receipt issuance away from its declared protected owner yields duplicate-framework-owner; incompatible or undeclared allocations also remain explicit conflicts |
| LR03 | Missing compatible required role, required product, duty or role layout yields a gap; candidates cannot erase the demand |
| LR04 | Matching intent plus complete structural coverage and no conflict permits structurally_covered; positive role_support explains allocations |
| LR05 | Every required capability needs an explicit established assertion; missing or non-established states block readiness |
| LR06 | Different intent basis or absent project intent yields invalidated; no layout is generated for it |
| LR07 | All candidate_state, conflict, gap and invalidated rows remain in the result; elaboration is not review approval |
| LR08 | runtime_ready is derived only when the declared structural/capability conditions hold; mixed positive/negative capability states remain blocked |

The four capability gates describe full qualification, not isolated source presence:
source-load includes the required build/load/recovery closure; capture-origin needs
authenticated origin/currentness; method-validation needs actual selected-method
receipts; authority needs real roles/grants and applicable review/use decisions.
The observed Scope run supplies useful source evidence but does not close those
full gates. Candidate capability assertions in this model are not their issuers.

The finite program uses existing typed string relations, stratified negation and
bounds (4096,4096,4096). A fresh native Session receives the full Scenario batch;
incomplete evaluation is rejected. Closed-world gaps concern this declared batch,
not omniscient knowledge about the repository. The application does not scan prose,
infer source truth from an LLM statement, issue A/E/W/use, authenticate capabilities,
run Aitia or grant authority. Even a future declared runtime_ready row would only
mean these model premises hold; authenticated runtime acceptance remains P0--P9.

protected owner policy or treat its own capability assertions as evidence.

organization and recorded outcomes. Their updates in this slice are explicit paired
maintenance. Automatic Org/D2 synchronization and model merge/reconciliation are open.
